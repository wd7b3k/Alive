# Response / Handoff — живой QA: зелёный CI и два дубликата в каталоге

Дата: 2026-08-21

## Result

Починил CI (PR #12 стал полностью зелёным) и нашёл на живом деплое два настоящих
дефекта контента, которые невозможно было увидеть ни статическим анализом, ни
локальной сборкой без логина. Оба — один и тот же класс ошибки, оба исправлены
одной идемпотентной миграцией с сохранением истории. Отдельно зафиксирована, но
сознательно не исправлена, одна содержательная дыра в кураторском контенте.

## 1. CI: джоба `rls-isolation` падала на каждый push

`supabase/tests/local/run.sh` имел в git режим `100644` вместо `100755` — файл
попал в репозиторий через мост к устройству владельца, а тот переносит содержимое,
но не POSIX-права. CI падал на `Permission denied`, exit code 126, то есть тест
изоляции RLS **не выполнялся вообще** — при этом внешне выглядело так, будто в
проекте есть работающая проверка безопасности. Это худший вид красноты: не «тест
нашёл проблему», а «проверки нет, но её присутствие задекларировано».

Исправлено двумя слоями: режим возвращён на `100755` (через
`git update-index --cacheinfo`, blob не тронут — без мусорного diff по
line-endings), и в `frontend-ci.yml` вызов сделан явным `bash run.sh`, чтобы тот же
класс поломки не повторился при будущих синхронизациях через мост. Перед пушем
прогнан **ровно тот путь, которым идёт CI** (env `PGHOST`/`PGUSER`/`PGPASSWORD`,
TCP-подключение с паролем, от имени обычного пользователя, не `postgres`) — ALL PASS.
После пуша: все 3 проверки PR #12 зелёные.

## 2. Два побайтово одинаковых дубликата в публичном каталоге

Найдено глазами на живом деплое (`Связки` → «Что система уже видит»), затем
подтверждено программно через DOM (29 карточек, 28 уникальных) и по исходникам
миграций.

Один и тот же объект заведён под двумя кодами, дважды:

| легенда | legacy-код (initial migration) | канонический (product-depth) | связей у legacy | связей у канонического |
|---|---|---|---|---|
| «После пробуждения» | `morning` | `wake_up` | 0 | 4 |
| «Стакан воды» | `water` | `water_pause` | 0 | 5 |

Причина одна: `20260815215100_v3_product_depth_catalog_a.sql` ввёл канонические
записи, но не удалил исходные из `20260815170000_v3_platform_initial.sql`, и обе
остались `published`.

**Почему это не косметика.** У legacy-кодов ноль курированных связей
триггер→замена. `pickReplacements` (`app/src/data.ts`) устроен как каскад:
`[...mapped, ...по потребности, ...все]`. Поэтому выбор дубликата не ломает поток —
пользователь всё равно получает три карточки — но **тихо отключает ситуативный
подбор** и скатывается на подбор только по потребности. То есть ровно то, что
продукт обещает как своё отличие («не список полезных привычек, а ответы под
ситуацию»), молча деградирует, без единого сигнала. Хуже того, эпизоды
расщепляются между двумя кодами: реальный утренний паттерн пользователя
недосчитывается — а его обнаружение и есть смысл существования продукта.

Для «Стакан воды» дубликат ещё и виден напрямую: у `water` потребности
`['pause','oral_sensory']`, у `water_pause` — `['pause','switch','closure']`, общая
`pause`. При выборе этой потребности обе записи одинаково проходят фильтр и
получают одинаковый бонус к скору, то есть в одной тройке предложений могут
оказаться две визуально идентичные карточки.

**Исправление**: `supabase/migrations/20260821120000_v3_dedupe_legacy_morning_trigger.sql`.
Сначала переносит историю на канонические коды (`episodes.trigger_code`,
`episode_actions.replacement_code`, `user_links.preferred_replacement_code`), потом
удаляет сироты — и только после защитных проверок: если канонической записи нет или
после переноса на legacy-код кто-то всё ещё ссылается, миграция падает с явной
ошибкой, а не молча теряет данные. Порядок именно такой, потому что
`episodes.trigger_code` — FK без `on delete cascade`: удаление «сначала» просто
заблокировалось бы, а `cascade` в других таблицах уничтожил бы историю.

**Проверено локально на настоящих миграциях**, с историей на обоих legacy-кодах:
перенос 1/1/1 → всё на канонических кодах, суммарно ничего не потеряно, дубликатов
0, каталог 28/45, все 96 связей не затронуты, повторный прогон безопасен
(идемпотентность), полный набор RLS-тестов по-прежнему ALL PASS.

**Не применено к живому Supabase**: у меня нет и не должно быть таких credentials.
Применение — действие владельца.

`docs/CURRENT_STATE.md`: цифры каталога исправлены 29/46 → 28/45 (ранее
задокументированные значения считали дубликаты) с пояснением причины.

## 3. Найдено, не исправлено: триггеры без курированных замен

Четыре published-триггера не имеют ни одной связи с заменами: `tension`
(«Напряжение / сложная мысль»), `after_task` («После завершённого дела»), `other`
(«Другое») и `morning` (удаляется миграцией выше). Для `other` это, вероятно,
замысел. Но `tension` — один из самых частых реальных триггеров курения, и
выбравший его пользователь молча получает подбор только по потребности вместо
обещанного ситуативного.

**Сознательно не чиню**: это пробел в кураторском контенте, а не ошибка в коде.
Какие именно замены привязать к «напряжению» — методическое решение владельца;
придумывать за него содержание продукта я не буду. Зафиксировано в `VALIDATION.md`.

## Что проверено на живом деплое

Экраны: Сегодня, Связки, Путь, Смыслы (все под реальным логином владельца). На всех —
0 горизонтального overflow, 0 touch-target меньше 44px. Логотип на реальном деплое
ветки (`redesign-v3-0-logo-followup.alive-aw2.pages.dev`) отрисован как узнаваемый
Om/ALIVE — первое подтверждение бренда на живой инфраструктуре; на production
(`alive-aw2.pages.dev`, старая сборка) в шапке по-прежнему виден битый ассет, что
независимо подтверждает необходимость фикса из PR #12.

В аккаунте владельца **ничего не создано и не удалено**: модалки, которые пишут
данные (поток тяги, «Никотин уже был», «Итоги дня»), намеренно не доводились до
сохранения — QA не должен оставлять мусорные эпизоды в личных данных.

## Чего этот проход НЕ покрыл

- **Мобильные ширины за логином.** Расширение браузера не отдаёт управление размером
  viewport (окно ресайзится, `window.innerWidth` остаётся 1920), поэтому весь
  mobile safe-zone чеклист за логином остаётся непроверенным. Пре-логин экраны
  проверены ранее локально через Playwright на всех 5 baseline-ширинах.
- Модалки потока тяги (4 шага), быстрый лог никотина, вечерний чек-ин, Профиль —
  не пройдены до конца, т.к. это записывает данные в реальный аккаунт.
- Живой RLS smoke-test с **двумя** реальными Google-аккаунтами — по-прежнему
  требует второго аккаунта владельца.
- Деплой и тест Edge Function `delete-account`.

Релиз не объявлен `v3.0 RELEASED` — решение владельца по `RELEASE_POLICY.md` §10.
