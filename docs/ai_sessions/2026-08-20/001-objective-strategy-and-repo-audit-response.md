## 1. Аудит документации vs реальный git

### 1.1 Главное расхождение: репозиторий не заканчивается на `main` — и ни один
   канонический документ этого не фиксирует

Проверено: `git branch -a`, `git log --graph --oneline --all`, `git merge-base --is-ancestor`,
`git rev-list --count`.

`main` (HEAD `86b4608`, "ALIVE v3.0: deep interface redesign") — последний коммит
**2026-08-15**. В remote при этом присутствуют ещё 11 веток, из них 7 веток вида
`agent/*` с коммитами вплоть до **2026-08-18**, ни одна не смержена в `main`:

| Ветка | Коммитов впереди `main` | Последний коммит |
|---|---|---|
| `agent/owner-vision-delivery-protocol` | 225 | 2026-08-18 |
| `agent/v4.0.0-alpha.1-hotfix.1` | 225 | 2026-08-18 |
| `agent/v4.0.0-alpha.1` | 222 | 2026-08-18 |
| `agent/r1-data-evidence-admin` | 100 | 2026-08-17 |
| `agent/v3.1-behavioral-depth-together` | 67 | 2026-08-17 |

| `v3.0-hardening` / `v3.0-platform` / `v3.0-redesign` / `migration/standalone-repo` | 1–30 | 2026-08-15 |

Значимо не то, что существуют feature-ветки (это ожидаемо по `AGENTS.md` "Git workflow"),
а то, что:

- на `agent/v4.0.0-alpha.1` и `agent/v4.0.0-alpha.1-hotfix.1` уже существуют полноценные
  release units `releases/v4.0.0-alpha.1/` и `releases/v4.0.0-alpha.1-hotfix.1/`
  (README/REQUIREMENTS/VALIDATION/ROLLBACK каждый) — то есть версия **4.0.0-alpha**
  уже присвоена в remote, при том что `v3.0` ещё не объявлен RELEASED. Это прямое
  расхождение с `docs/RELEASE_POLICY.md` §3 ("Нельзя создавать `3.0.1`, если `3.0` не
  был принят/выпущен" — тем более нельзя `4.0.0-alpha`) и §10 ("AI не должен
  самостоятельно повышать версию... без фактического подтверждения"), и с
  `docs/ROADMAP.md` ("Переходы идут по evidence gates, а не потому, что следующая
  версия уже описана" — а после v3.0 по roadmap следует v3.1 Together, не v4.0);
- на `agent/r1-data-evidence-admin` уже есть `releases/r1-data-evidence-admin/` —
  это scope v3.2 (Admin/Product Intelligence по `ROADMAP.md`), начатый до того как
  v3.0 или v3.1 прошли свой evidence gate;
- ни `README.md`, ни `docs/CURRENT_STATE.md`, ни `docs/INFRASTRUCTURE_STATE.md`, ни
  `docs/ROADMAP.md` на `main` не упоminают о существовании этих веток вообще. Новый
  читатель, следующий предписанному в `AGENTS.md` порядку чтения, не узнает о ~225
  коммитах работы в remote того же репозитория.

Это прямо бьёт по собственному ключевому правилу репозитория (`AGENTS.md`,
"REPO = единственный source of truth"): значительная часть того, что реально
происходило в этом repo, не восстановима из документов на `main` без ручного обхода
`git branch -a`.

**Важное уточнение к прошлому проходу.** В привязанном Claude-проекте уже лежит более
ранний summary этого же дня, где сказано: "по факту в remote git осталась только
`main`, весь путь уже слит". Это утверждение проверено в этой сессии напрямую и
**не подтвердилось** — оно ошибочно. Отчёт исправляет его, а не повторяет.

Это не обязательно означает злого умысла или потерянной работы — вероятно, это
результат нескольких параллельных agent-сессий, которые не были доведены до PR/merge
или ревью владельца. Но пока это не отражено в документах, "repo = source of truth"
верно только для `main`, а не для repo в целом, и это стоит внести как явную оговорку,
пока владелец не решит, что делать с этими ветками (см. раздел 4/5).

## 2. Оценка стратегии

### 2.1 Что реально отличает продукт (проверено по документам и коду, не только
   заявлено)

- **Не quit-tracker.** Core loop `триггер → потребность → 3 персональные замены →
  результат → обучение` (`docs/PRODUCT_STRATEGY.md` §3) реализован в коде
  (`RedesignApp.tsx`, `metrics.ts`) как реальная схема данных, а не просто лозунг:
  raw-события отделены от derived-статистики (`docs/DATA_MODEL.md`,
  `FR-V3-041/044`), удаление тестового эпизода пересчитывает производные метрики
  без переписывания истории.
- **Мульти-продуктовость с честной эквивалентностью.** cigarette/hookah/vape как
  раздельные raw-продукты, `ALIVE Equivalence v1` явно маркирован как behavioural
  heuristic, а не медицинский эквивалент (`FR-V3-042/043`, подтверждено текстом на
  `/experiment` в коде). Это методологическая дисциплина, редкая для personal quit-app.
- **Некоммерческий charter как условие доверия, а не просто лозунг.** Явно завязан
  на privacy-обещания (`PROJECT_CHARTER.md` §2, `PRIVACY_AND_DATA.md` §2) — "если
  коммерческий статус изменится, принципы не меняются молча".
- **Hypothesis-driven roadmap с явным GO/ITERATE/PIVOT/STOP** (`HYPOTHESES_AND_METRICS.md`,
  "Первый pilot evidence gate") — вместо открытого roadmap роста.
- **Nothing unexplained + neutral language как архитектурное, а не косметическое
  требование** — "эпизод" вместо "провал", отсутствие leaderboard на `Вместе`.

### 2.2 Риски именно сейчас (не общие, привязаны к текущему состоянию)

1. **Governance-риск от раздела 1.1.** Пока ветки `agent/*` существуют
   несинхронизированными с документами, обещание "repo = единственный source of
   truth" фактически не выполняется для всего remote, только для `main`. Если кто-то
   (включая будущую AI-сессию) откроет `agent/v4.0.0-alpha.1`, он может принять
   несмерженный, неревьюженный код за принятое состояние продукта — прямое нарушение
   собственного правила AGENTS.md "решение, которого нет в git, не считается принятым",
   потому что *технически* эти решения в git есть, просто не в `main` и без
   владельческого review.
2. **Release-gate — монолитный барьер, а не слоёный.** Текущий `v3.0` gate (RLS
   isolation, два реальных Google-пользователя, export/delete Edge Function, 5
   viewport visual QA) — единый список, который *обязателен целиком* для
   "v3.0 RELEASED", и при этом пункты вроде "Google login для минимум двух
   пользователей" и RLS isolation в принципе не проверяемы при одном единственном
   реальном пользователе (самом авторе). Это значит, что author-only реальное
   тестирование на своём телефоне формально не может продвинуть чек-лист ни на пункт,
   хотя большинство privacy/RLS-рисков к нему просто неприменимы технически (нет
   второго tenant).
3. **Нет операционализированного канала качественной обратной связи.** И
   `HYPOTHESES_AND_METRICS.md` ("user-reported confusion", "qualitative feedback"),
   и `ROADMAP.md` (гейт v3.1) называют качественную обратную связь обязательным
   входным сигналом для GO/ITERATE/PIVOT — но ни один документ не описывает механизм
   сбора (форма, интервью, периодичность). Без этого 14-дневное pilot-окно рискует
   закончиться без структурированного качественного сигнала, только логами.
4. **Secret-scan заявлен как факт, но не как пройденный тест.** `CURRENT_STATE.md`
   утверждает "Service-role/OAuth secrets are not stored in frontend/repo" как
   свершившийся факт архитектуры, а `VALIDATION.md` держит "browser bundle secret
   scan PASS" в разделе незавершённого. Архитектурная гарантия (Google OAuth без
   собственного пароля, publishable key browser-safe) правдоподобна, но
   формулировка в CURRENT_STATE читается увереннее, чем формальный статус проверки.
5. **Не риск, а честная сильная сторона:** нет самомаркетинга/монетизации —
   поэтому большинство "классических" стратегических рисков (growth pressure,
   engagement-farming, ad-driven UX) здесь структурно отсутствуют по конструкции
   charter, а не по недосмотру.

### 2.3 Улучшения без нарушения non-commercial charter

- Закрыть governance-разрыв из 2.2.1: явная инвентаризация веток в
  `INFRASTRUCTURE_STATE.md` (даже если решение — "заброшено, не мержить") — это
  документационная, не продуктовая работа, charter не затрагивает.
- Определить конкретный, лёгкий канал качественной обратной связи для 3–5 друзей
  (даже "три вопроса в Google Form после каждого эпизода использования 3+ дня
  подряд") — не противоречит charter (не монетизация, не реклама), закрывает риск 3.
- Явно продублировать в VALIDATION.md Blocker-риски REQUIREMENTS.md построчно (в
  частности `RISK-V3-008` UGC-consent, см. 1.6), чтобы список "выполнено/не
  выполнено" был полным зеркалом заявленных Blocker'ов, а не подмножеством.
- Добавить README-ссылки на три "BLOCKING" документа (1.5) — нулевая стоимость,
  прямое исправление собственного правила "восстановить состояние без чата".

## 3. Ближайший релиз для реального теста

Scope взят из существующих `releases/v3.0-platform/REQUIREMENTS.md` и `VALIDATION.md`
без добавления нового scope, только пересортировка того, что уже там написано.
REQUIREMENTS.md сам маркирует четыре риска как явный **Blocker**: `RISK-V3-001` (RLS),
`RISK-V3-002` (secrets), `RISK-V3-008` (UGC consent), `RISK-V3-011` (functional/content
regression vs v2.7). Эта авторская разметка использована как основа деления ниже,
а не изобретена заново.

### 3.1 Блокирует безопасность/приватность **реальных других людей**

Актуально только когда в тесте участвует кто-то кроме самого автора:

- `RISK-V3-001` / `FR-V3-013/014` — RLS isolation. VALIDATION.md: `user A → private
  rows user B = denied` — **не пройдено**.
- Предпосылка к предыдущему — `Google login PASS минимум для двух пользователей`
  (gate-пункт #3 REQUIREMENTS.md) — без второго реального пользователя тест
  RLS isolation физически невозможен.
- `RISK-V3-002` — secrets в browser bundle. VALIDATION.md: `browser bundle secret
  scan PASS` — заявлен архитектурно (см. 2.2.4), но не отмечен как пройденный тест.
- `RISK-V3-008` — UGC explicit-consent test. Отсутствует в VALIDATION.md как строка
  вообще (см. 1.6) — нужно либо добавить и прогнать, либо явно зафиксировать
  "не применимо для author-only, обязательно перед приглашением других людей".
- `PRIVACY_AND_DATA.md` §10 / REQUIREMENTS gate #9 — export/delete basic tests.
  VALIDATION.md держит в "требует следующего gate" — не пройдено.
- Authenticated Edge Function для полного удаления аккаунта — CURRENT_STATE.md
  прямо перечисляет как ещё не сделанное.

### 3.2 Функциональный Blocker, не privacy, но явно помечен как Blocker в
   REQUIREMENTS.md

- `RISK-V3-011` — "Новая архитектура приводит к функциональному/content regression
  относительно v2.7." VALIDATION.md: "v2.7 product-depth parity smoke-test PASS" —
  не пройдено. Это не про приватность, но REQUIREMENTS.md сам называет это Blocker,
  и без него даже author-only тест рискует тестировать регресс, а не продукт.

### 3.3 Чистая полировка / QA (не блокирует безопасность реальных людей)

- Om-asset canonical hash (1.3) — важно для бренд-доверия и явно волнует владельца
  по тону `V3_VISUAL_UX_BASELINE.md`, но технически не privacy/security риск.
- Визуальный parity/safe-zone review, 5-viewport smoke-test
  (360/390–430/768–820/1280/1440+).
- Конфликты primary/destructive-действий, перекрытие fixed-nav — в основном визуальный
  QA, но есть узкий не-privacy "safety"-угол: столкновение destructive-действия с
  primary может привести к случайной потере собственных данных пользователя. Стоит
  оставить в отдельной категории "низкий priority, но не игнорировать".
- Локальный `supabase db reset` воспроизводимость, финальная синхронизация
  docs/current-state — процессная гигиена, не блокер безопасности.
- "nothing unexplained" UX-ревью — важно для качества пилота, не для privacy/security.

### 3.4 Рекомендация по структуре ближайшего релиза

Существующее предложение "Author-only alpha vs Friends pilot" (уже присутствовавшее
в прежнем summary) в этой сессии подтверждается независимо, на основе деления выше,
а не переоткрывается заново:

- **(A) Author-only alpha** — реальное использование самим автором. Технически не
  требует пунктов из 3.1, которые предполагают второго человека (RLS isolation,
  two-user login, UGC-consent — если автор сам не отправляет UGC). Разумно требует
  прохождения 3.2 (иначе тест меряет регресс, а не продукт) и желательно — secret-scan
  из 3.1 (защищает инфраструктуру автора независимо от числа пользователей).
- **(B) Friends pilot** — приглашение реальных других людей. Требует **полного**
  существующего gate из REQUIREMENTS.md/VALIDATION.md без урезания, включая весь
  раздел 3.1 построчно и явное закрытие пробела по UGC-consent (1.6).

Ни (A), ни (B) не объявляются в этом документе состоявшимися — обе стадии остаются
решением владельца, фиксируемым через обновление `VALIDATION.md`/`CURRENT_STATE.md`
по факту.

## 4. Roadmap — подтверждение / корректировка по evidence gates

Структура `F0 → v3.0 (Platform+Core Loop) → v3.1 (Together) → v3.2 (Admin/Intelligence)
→ post-v3.2` в `docs/ROADMAP.md` **не требует структурных изменений** — она внутренне
непротиворечива и явно строится на evidence gates, а не предрешённой последовательности
версий.

Корректировка по факту, а не по стилю:

- Существование `agent/v4.0.0-alpha.1*`, `agent/v3.1-behavioral-depth-together`,
  `agent/r1-data-evidence-admin`, `agent/product-strategy-foundation` — это уже
  выполненная (пусть и несмерженная) работа поверх/вперёд заявленного roadmap.
  Формально это не меняет сам roadmap-документ, но означает, что "правило roadmap"
  ("переходы идут по evidence gates") в какой-то момент нарушалось на уровне
  выполнения, а не описания. Рекомендация: явное владельческое решение — что из этих
  веток (а) абандонить, (б) частично забрать как input в v3.1/v3.2 планирование без
  повышения версии задним числом, (в) через отдельный ADR признать как реально принятый
  scope. Без этого шага сам roadmap продолжает быть верным документом, но переставшим
  быть полной картиной того, что уже сделано в repo.
- Ранее предложенная метка **v3.0 Pilot-Ready** между "код готов" и формальным
  "v3.0 RELEASED" подтверждается как разумное, низкорисковое дополнение: она не меняет
  scope (`CURRENT_STATE.md` уже фактически проводит это различие текстом "Deploying a
  v3.0 alpha for real testing does not mean the release gate is complete"), а просто
  даёт этому различию имя и чек-лист. Это документационное дополнение, не решение
  уровня ADR/владельческого гейта.
- До начала 14-дневного evidence-окна имеет смысл закрыть 2.2.3 (канал качественной
  обратной связи) — иначе одна из входных метрик gate ("qualitative feedback не
  указывает на shame/competition harm") не будет иметь источника данных.

## 5. Обоснование

**Продуктовое.** Приоритет — закрыть существующий REQUIREMENTS.md/VALIDATION.md gate
без нового scope: цель пилота — evidence по уже сформулированным гипотезам
(`HYPOTHESES_AND_METRICS.md`), а не рост или новые фичи. Это подтверждается собственной
стратегией проекта (§13 PRODUCT_STRATEGY.md, "что не строить раньше времени") и не
меняется этим ревью. Единственное реальное дополнение к продуктовому приоритету —
governance-разрыв из раздела 1.1/4: закрытие branch-дрейфа — не новый scope, а защита
уже заявленного главного правила репозитория (repo = source of truth), и логично
должно идти раньше, а не после следующего продуктового рывка.

**Доверие когорты.** Первая когорта — знакомые автора (`PROJECT_CHARTER.md` §7),
которые будут проверять честность продукта пристальнее анонимных пользователей.
Privacy-by-design и neutral/non-shaming язык здесь функционируют как условие участия,
а не украшение — что подтверждается тем, что этот язык реально реализован в коде
(`Experiment`-компонент), а не только продекларирован в документах.

**Ценность репозитория как артефакта.** Дисциплина документации (release units,
FR/RISK-нумерация, hypothesis-gate язык, AI audit trail per session) — она
самостоятельная демонстрация продуктового мышления вне зависимости от судьбы продукта.
Эта оценка в данном ревью **условна**, не безусловна: пока ветки из раздела 1.1 не
инвентаризированы и не согласованы с документами на `main`, центральное обещание
самого артефакта ("репозиторий целиком отражает реальное состояние") выполняется
только частично. После закрытия этого разрыва оценка "репозиторий как артефакт"
может быть дана без оговорок.
