# Response / Handoff — репозиторий синхронизирован с production

Дата: 2026-08-21

## Result

Репозиторий снова описывает то, что реально работает у пользователей. Проверено не
на глаз, а сверкой поле-в-поле: база, собранная с нуля из миграций, совпадает с
production по агрегатным SHA-256 — по базовым полям всех 74 замен, по их
метаданным и по каталогу триггеров. В самом проде не изменено ничего.

## Что оказалось расхождением

Началось с одного дубликата, всплывшего в проверке миграции дедупликации, и
оказалось системным. Прод правился напрямую через Dashboard, мимо миграций:

| что | масштаб |
|---|---|
| замены, существующие только в проде | 29 |
| замены, переименованные в проде | 3 (`sensory_reset`, `meaning_card`, `meaning_read`) |
| колонки, добавленные мимо миграций | 20 (`replacements_catalog` +14, `triggers_catalog` +4, `episodes` +2) |
| evidence/curation-метаданные | заполнены у всех 74 строк прода, в репо отсутствовали полностью |

**Почему это был главный релизный риск.** В `VALIDATION.md` обязательным пунктом
релиза стоит `supabase db reset` — пересборка базы из миграций. Выполненный до этой
правки, он дал бы базу без 29 видимых пользователю замен, без всех метаданных
доказательности и без 20 колонок. То есть документированный шаг релиза уничтожал
боевой контент, и заявление «repo — единственный source of truth» фактически не
выполнялось.

## Что сделано

Две миграции, по решению владельца в направлении «прод — истина»:

- `20260821130000_v3_sync_production_schema_drift.sql` — колонки. Типы,
  nullability и умолчания сняты из `information_schema` прода, а не выведены из
  кода. Всё через `if not exists`.
- `20260821140000_v3_sync_production_catalog_content.sql` — значения: 29 новых
  замен целиком, 6 изменённых строк, метаданные для 45 уже существовавших,
  категории и recognition-prompt для 28 триггеров.

Значения прочитаны из прода через PostgREST и воспроизведены дословно. **Ничего не
придумано**: ни одна замена, формулировка, оценка доказательности или ссылка на
источник не авторские. Базовые поля 39 замен, которые и так совпадали, намеренно не
переписываются — им дозаполняются только отсутствовавшие метаданные.

Отдельно: `episodes.user_trigger_id` в проде — обычный `uuid` без внешнего ключа.
Воспроизведён ровно таким. Добавлять ссылку на `user_links`, которой в проде нет,
я не стал: свежая база оказалась бы строже реальной и отвергала бы строки, которые
прод принимает.

## Как проверено

Собрал базу с нуля из всех миграций и сверил с продом:

- агрегатный SHA-256 по базовым полям 74 замен — `ae6a44085448fa99` с обеих сторон;
- агрегатный SHA-256 по метаданным 74 замен — `daa9b0a76cc67273` с обеих сторон;
- агрегатный SHA-256 по каталогу триггеров — `5c33118b49a860fe` с обеих сторон;
- объёмы 74 / 28 / 96 совпадают;
- обе миграции идемпотентны (повторный прогон — no-op, 74 строки остаются 74);
- полный набор RLS-тестов — ALL PASS.

## Поправка к моему промежуточному отчёту

В процессе я сначала померил и сообщил, что «разошлись все 45 существующих строк».
Это была ошибка моего метода сравнения, а не реальность: при перепроверке совпали
39 из 45, разошлись 6. Фиксирую прямо, потому что на основании первой цифры можно
было принять куда более разрушительные решения.

## Что остаётся владельцу

- Применять эти две миграции к проду **не нужно** — они описывают то, что там уже
  есть, и являются no-op. Они нужны, чтобы `supabase db reset` и любая свежая среда
  воспроизводили прод.
- Продуктовое решение: `meaning_read` и `meaning_card` в проде теперь называются
  одинаково — «Прочитать своё «Зачем»». Похоже на следствие переименования
  терминологии со «Смыслов» на «Зачем»: два разных ответа схлопнулись в одно
  название, и пользователь может увидеть в подборе две одинаковые карточки. Это
  вопрос содержания, а не техники — не трогал.
- Отдельная гигиена процесса: чтобы расхождение не накопилось заново, правки
  каталога стоит вносить миграцией в репозитории, а не в Dashboard. Это решение
  владельца, здесь только фиксирую.

Релиз не объявлен `v3.0 RELEASED` — решение владельца по `RELEASE_POLICY.md` §10.
