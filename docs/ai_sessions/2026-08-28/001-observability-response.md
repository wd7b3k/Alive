## Что найдено при инвентаризации

Первый черновик плана предполагал строить слой событий с нуля. Это было неверно.

Слой построен ещё в августе: `analytics_events` с пятнадцатью колонками продуктовой
семантики, `system_errors` с отпечатком вместо текста, `analytics_reason_catalog`,
витрины `admin_product_health` и `admin_hypothesis_metrics`, и **десять триггеров,
пишущих события на сервере сами** — профиль, первичная настройка, цель, Связка,
действие в эпизоде, завершение эпизода, отметка дня, событие расхода.

Слой односторонний: он записывает факты, дошедшие до базы, и ничего из того, что
происходит до записи и вместо неё. В приложении **два** места, откуда вызывается
`trackEvent`.

Пять структурных дыр, каждая закрывает класс вопросов:

1. **Нет анонимного посетителя.** `user_id` ссылается на `profiles`, политика требует
   `auth.uid() = user_id`. Событие до входа записать физически нельзя, значит шаг
   «визит → регистрация» своими средствами не считается вообще.
2. **Нет сессии.** Не отличить «зашёл трижды по разу» от «сидел час» и не увидеть обрыв
   на шаге — главный различающий признак в модели оттока.
3. **Нет источника** — utm, реферер, поисковая система нигде не хранятся.
4. **Нет версии сборки и платформы**, хотя `buildInfo` на клиенте уже есть.
5. **Нет региона.**

Плюс время события только серверное: запись из офлайна получит время доставки.

## Два дефекта в `app/src/services/counters.ts`

Оба чинятся на этапе счётчиков, до включения в прод:

- заглушка `gtag` пушит в `dataLayer` обычный массив вместо объекта `arguments` — GA4
  такие команды не разбирает, счётчик молчит при внешне рабочем коде;
- стаб `ym` не ставит метку времени `.l`, из-за чего Метрика теряет измерение времени
  загрузки. Параметр `anonymize_ip` — из Universal Analytics, в GA4 игнорируется.

Отдельно: комментарий модуля объявляет правило «счётчики только до входа». Оно
противоречит решению владельца от 28.08 и переписывается вместе с ADR-0014.

# Промт для агента на машине владельца

Ты работаешь на машине владельца через VS Code Remote-SSH и имеешь доступ к боевому
серверу Habitoff (`alive@5.129.222.119`) и ко второму серверу, где будет сторож.

**Сначала прочитай** `AGENTS.md`, `docs/INFRASTRUCTURE_STATE.md`, `infra/monitoring/README.md`
и `docs/RUNBOOK_ALERTS.md` этой ветки. Прямой `psql` на боевой базе — только чтение.

## Шаг 0. Инвентаризация сервера — до всего остального

Ответь фактами, а не предположениями, и запиши ответы в `docs/INFRASTRUCTURE_STATE.md`:

1. Какой коммит собран на проде (`/srv/alive/current/version.json`), совпадает ли с
   `origin/main`. `node scripts/check-deploy-drift.mjs`.
2. Настроены ли бэкапы: есть ли таймер, есть ли дампы в `/srv/alive/backups`, когда последний.
   Если нет — это блокирующий пункт перед пилотом, и он важнее остального в этом промте.
3. Точные имена контейнеров (`docker compose ps`) — в скриптах предполагается
   `supabase-db`, проверь и поправь `DB_CONTAINER`.
4. Пишет ли Caddy журнал доступа в JSON и куда. Если журнала нет — включи его в
   `Caddyfile` и укажи путь в `CADDY_ACCESS_LOG`; без него проверка `caddy_5xx` бесполезна.
5. Стоит ли `python3` на боевом сервере (нужен для `caddy-errors.sh` и экранирования).
6. Есть ли `whois` (нужен для срока домена).
7. Второй сервер: ОС, адрес, есть ли `python3`, открыт ли порт.

# Как прогнать проверки перед PR

Пошагово, на машине владельца. Ветка уже выкачана в рабочее дерево, ставить ничего,
кроме зависимостей, не нужно.

## 1. Перейти в рабочее дерево и поставить зависимости

```powershell
cd C:\Users\ПК\Projects\alive\Alive.worktrees\observability\app
npm ci
```

`npm ci` ставит ровно то, что записано в `package-lock.json`, и не трогает основной клон:
у рабочего дерева свои `node_modules`. Первый раз это несколько минут.

## 2. Типы

```powershell
npm run typecheck
```

Здесь ошибки наиболее вероятны: этой сессией добавлены `services/visitor.ts`,
`modules/analytics/` и правки в `analytics.ts`, `AppRouter.tsx`, `shared.tsx`,
`useBootstrapSession.ts`, `RedesignApp.tsx`, и ни одна из них не прошла компилятор.

Что ожидаемо всплывёт:

- **`supabase.rpc` с новыми именами функций.** Если клиент типизирован сгенерированной
  схемой, `alive_touch_visitor`, `alive_record_anon_event`, `alive_claim_visitor` и шесть
  `admin_*` в ней отсутствуют, пока схема не перегенерирована. Лечится генерацией типов
  после применения миграций — или, если типы в проекте не генерируются, ошибок не будет вовсе.
- **`window.ym` в `visitor.ts`.** Глобальный тип объявлен в `counters.ts`; если модуль не
  подтянулся, добавить импорт или объявление.
- **Неиспользованное после правок** — `eslint` с `--max-warnings=0` не прощает.

## 3. Линтер и формат

```powershell
npm run lint
npm run format:check
```

`format:check` почти наверняка ругнётся: файлы писались не через prettier. Исправляется
одной командой `npm run format`, после неё стоит перечитать диф.

## 4. Тесты

```powershell
npm test
```

Существующие тесты трогают `sanitizeMetadata`, инварианты CSS, SEO и вёрстку. Правки
этой сессии их задевать не должны; если падает `css-invariants` — значит, где-то
появился дублирующий селектор верхнего уровня, и это моя ошибка, а не тест.

## 5. Сборка

```powershell
npm run build
```

Она включает `tsc --noEmit` ещё раз и собирает бандл. Зелёная сборка — условие PR.

## 6. Что делать с найденным

Правки коммитить в эту же ветку отдельным коммитом с честным описанием, что именно не
сошлось. Если правка меняет смысл, а не форму — например, оказалось, что RPC называется
иначе или роль читается не оттуда, — это стоит отдельной строки в этом файле: следующая
сессия должна знать, где написанное вслепую разошлось с реальностью.
