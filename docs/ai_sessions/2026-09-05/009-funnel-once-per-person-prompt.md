# Отметка вехи привязана к браузеру, а не к человеку

Найдено при проверке работы по 001 (коммит 013868d, выложено 05.09.2026).
Сама работа принята: цели дошли до всех шести вех, договор воронки держит тест,
дата включения счётчиков взята из данных. Ошибка одна, и она не в целях.

## Что не так

`markFunnelStageOnce` (`app/src/services/visitor.ts:100`) хранит достигнутые вехи
одной строкой в `localStorage`, без идентификатора человека. `trackStageOnce`
(`app/src/services/analytics.ts:246`) спрашивает эту отметку **до** записи события:

    if (!markFunnelStageOnce(stage)) return;
    trackEvent(userId, { event_type: 'funnel_stage', ... });
    trackGoal(STAGE_TO_GOAL[stage]);

Отсюда два следствия, и второе хуже первого.

1. Очистка данных браузера возвращает все вехи заново — воронка считает их дважды.
2. **Второй человек в том же браузере не попадает в воронку вообще.** Не только
   цель в кабинете — своя строка `funnel_stage` тоже не пишется, потому что
   `return` стоит раньше. Это не редкий случай: свой же тестовый вход вторым
   аккаунтом, общий домашний компьютер, вход после выхода. Данные при этом не
   выглядят битыми, они выглядят пустыми — то есть ошибка неотличима от
   «людей нет».

Свой слой знает `user_id` и потому может дедуплицировать надёжно; браузер не может.
Одинаковая защита для двух разных получателей — и есть ошибка.

## Что сделать

1. Отметку хранить по человеку: ключ вида `habitoff:funnel:v2:<user_id>`, для
   анонимной вехи `landing` — по идентификатору посетителя из `visitor.ts`.
   При выходе отметка текущего человека не переносится на следующего.
2. Свою строку `funnel_stage` писать **всегда**, а отметку спрашивать только перед
   `trackGoal`. Дедупликацию своего слоя делать в SQL: первая по времени строка на
   пару (`user_id`, `funnel_stage`) — `distinct on`. Так очистка браузера и второй
   аккаунт перестают влиять на собственные данные вообще, а на кабинеты влияют
   ровно настолько, насколько кабинеты в принципе умеют считать людей.
3. Витрины, которые считают вехи по `analytics_events`, привести к этой
   дедупликации — иначе двойной счёт просто переедет из клиента в отчёт.

## Тесты

- К `visitor-funnel.test.ts`: две разные пары «человек — веха» в одном хранилище;
  вторая обязана пройти. Сейчас этот тест покраснеет — он и должен.
- К договору воронки: `trackStageOnce` записывает событие даже тогда, когда веха
  уже отмечена. Проверить на негативном контроле, что возврат `return` наверх
  делает тест красным.
- Смоук на витрину с `distinct on`: две строки одной вехи одного человека дают
  единицу.

## Отдельно, не ошибка, но читать надо с оговоркой

`episode_with_result` отправляется безусловно сразу за `first_episode` /
`repeat_episode` в том же обработчике — сценарий тяги иначе закончиться не умеет.
Значит, в воронке шаг «эпизод с результатом» будет ровно равен предыдущему, и
читать его как конверсию нельзя до тех пор, пока не появится второй способ завести
эпизод. Написать это подписью у шага на `/admin/analytics`, а не оставлять на
догадку.

## Сдача

Как в прошлый раз: четыре команды зелёные с выводом, отдельно «проверено
запуском» и «не проверено и почему», отдельная ветка.
