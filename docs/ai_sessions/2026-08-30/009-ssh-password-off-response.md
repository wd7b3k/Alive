# Запрет, который лежал на диске и не действовал

Ответ на `009-ssh-password-off-prompt.md`. Ветка `infra/ssh-password-off` от
`origin/main` = `8afbce4`.

## Вход по паролю

Два уточнения к постановке, и оба меняют, что именно надо делать.

**Первое: запрет пароля уже был написан — дважды.** `/etc/ssh/sshd_config.d/99-alive.conf`
содержит `PasswordAuthentication no` с 26.08, а сегодня в 18:16 появился ещё и
`00-no-password.conf` с тем же содержимым. Ни один из них не работал так, как выглядел.

Причина — порядок чтения. `sshd_config` подключает каталог первой строкой, файлы
читаются лексически, и для большинства ключей **выигрывает первое встреченное значение,
а не последнее.** Это противоположно поведению `conf.d` у большинства демонов:

| Файл | Значение | Кто положил |
|---|---|---|
| `50-cloud-init.conf` | `PasswordAuthentication yes` | образ провайдера |
| `99-alive.conf` | `PasswordAuthentication no` | настройка сервера 26.08 |

До файла с префиксом 99 дело не доходило. Настройка выглядела сделанной четыре дня,
`sshd -T` всё это время отвечал `yes`, и к 30.08 в журнале накопилось **3692 неудачных
попытки и 460 забаненных адресов**.

**Второе: `00-no-password.conf` был написан, но не применён.** Служба не перечитывала
конфигурацию с 26 августа:

```
$ systemctl show ssh -p ExecMainStartTimestamp
ExecMainStartTimestamp=Wed 2026-08-26 17:33:04 UTC
$ stat -c %y /etc/ssh/sshd_config.d/00-no-password.conf
2026-08-30 18:16:28 +0000
```

То есть живой демон продолжал принимать пароли, хотя на диске лежал запрет. Ровно тот
же класс ошибки, что и с выкладкой: файл на диске ничего не доказывает, доказывает
только состояние работающей службы.

Файл внесён в репозиторий (`infra/ssh/sshd_config.d/00-no-password.conf`, с разбором
ловушки в комментарии), установлен оттуда и применён. Порядок соблюдён требуемый:
`sshd -t`, затем проверка входа по ключу новой сессией, и только потом `reload` —
не `restart`, который порвал бы текущие сессии.

## fail2ban

Мусора не оказалось. Проверено, а не предположено:

```
$ ls -la /etc/fail2ban/jail.d/
-rw-r--r-- 1 root root 117 Jun 10  2024 defaults-debian.conf
-rw-r--r-- 1 root root  52 Aug 30 18:00 ignoreip.local
-rw-r--r-- 1 root root  81 Aug 26 17:32 sshd.local
```

`ignoreip.local` — обычный файл с корректным `[DEFAULT] ignoreip`, каталога
`ignoreip.local/jail.d/i` не существует. Удалять нечего, и ничего не удалено.

Заодно стало понятно происхождение самого файла: он появился в 18:00 и содержит адрес
рабочей машины владельца. Нужен он по делу — серия отказов по проверке ключа хоста
попадает в тот же счётчик, что и подбор пароля, и отрезает доступ на час. Именно так
эта сессия и потеряла ssh на час в прошлом заходе.

## Владелец каталога выкладки

Записан в `docs/INFRASTRUCTURE_STATE.md` отдельным разделом: `/srv/alive/repo`
принадлежит `alive:alive`, выкладка идёт от `alive`, git отказывается читать чужой
репозиторий, а `npm ci` и сборка от root оставляют в нём файлы чужого владельца.
Отдельно оговорено исключение — `/srv/alive/backups` остаётся root-овым с правами 600
намеренно.
