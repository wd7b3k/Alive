## Не сделано: выкладка

`ssh` на боевой сервер перестал отвечать сразу после первого успешного подключения.
Первая команда прошла нормально (`whoami` → `alive`, `readlink -f /srv/alive/current` →
`releases/20260830-162618`), затем соединения начали упираться в таймаут на этапе
`banner exchange`: TCP принимается, обмен версиями не начинается.

Между этими двумя состояниями было три неудачных подключения из второго окружения
оболочки, где клиент `ssh` не смог прочитать `known_hosts` — путь к домашнему каталогу
содержит кириллицу и приезжает в `ssh` испорченным (`/c/Users/\317\312/.ssh/...`).
Три отказа по проверке ключа хоста подряд — обычный повод для защиты от перебора
закрыть адрес. Попытки прекращены, чтобы не продлевать блокировку.

**Продукт при этом работает.** Проверено: apex — 200 за 0,46 с, `/auth/v1/health` и
`/rest/v1/` — 401 (шлюз требует `apikey`, то есть жив), `https://www.habitoff.ru/` —
301 на apex, сертификат в порядке. Недоступен ровно `sshd`.

Второй сервер (сторож) как обходной путь не годится: у него сменился ключ хоста.
Принимать новый ключ вместо владельца нельзя.

1. Проверить, не закрыт ли адрес защитой от перебора (`fail2ban-client status sshd` или
   `journalctl -u ssh --since -1h` с консоли провайдера), и разблокировать.
2. Отдельно: у второго сервера (`89.125.209.26`) сменился ключ хоста. Если это была
   пересборка — обновить `known_hosts`; если нет — это вопрос безопасности.
3. Выложить:

```bash
cd /srv/alive/repo && git checkout main && git pull && /srv/alive/deploy.sh
node scripts/check-deploy-drift.mjs
```
