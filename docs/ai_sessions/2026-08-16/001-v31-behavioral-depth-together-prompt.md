# ALIVE v3.1 — согласованный scope

Дата: 2026-08-16

Статус: APPROVED BY OWNER

## Цель

Продолжить текущий ALIVE v3.0 product alpha без редизайна с нуля и собрать v3.1 как углубление поведенческого движка плюс ранее запланированный раздел `Вместе`.

Канонический репозиторий: `wd7b3k/Alive`.

Исторический исследовательский источник: `wd7b3k/HumanOS/tree/main/projectsv1.0`.

## Обязательный scope

1. Провести evidence-first исследование современных методов прекращения никотиновой зависимости и отдельно — исследование smoking myths / outcome expectancies.
2. Существенно расширить каталог Замен: дыхание, grounding, внимание, движение, пауза, сенсорика, оральные/ручные действия, напитки, еда, фокус, эмоциональная разгрузка, социальный контакт, изменение контекста, Смыслы, награды, НЗТ и другая доказательная поддержка.
3. Адаптировать лучшие простые механики из HumanOS v1.0: стопы на полу, давление/отпускание, длинный выдох, 5-4-3/3-2-1, сужение внимания, вода, тишина, движение и другие короткие протоколы саморегуляции.
4. Улучшить Replacement Engine: 3 предложения должны по возможности представлять разные механизмы, учитывать потребность, триггер, продукт, силу тяги и личные outcomes.
5. Улучшить guided craving flow: заметный прогресс, явное `Шаг N из M`, кликабельные уже пройденные этапы, корректная инвалидизация downstream choices после изменения более раннего выбора.
6. Весь пользовательский интерфейс — на русском языке. Не оставлять внутренние англоязычные термины в пользовательском UI.
7. Не использовать точки в заголовках. Убрать CTA `Меня тянет`; использовать ясный product-aware CTA: `Хочу закурить`, `Хочу затянуться`, `Хочу покурить кальян`.
8. Добавить отдельную сущность `Мифы` как часть поведенческого движка, а не простой FAQ. Исследовать и seed-ить ключевые убеждения: успокоение, концентрация, удовольствие, скука, стиль/идентичность, вес, light/малое количество, НЗТ, вейп, контроль зависимости, срыв и др.
9. Миф должен уметь связываться с trigger/need/context и иметь private user relevance (`Похоже на меня` / `Не про меня`). Контекстный reminder — максимум один за короткий craving flow, с frequency cap.
10. Добавить `Факты` как мягкий постоянный evidence layer о рисках и выгодах отказа. Персонализация — вторична; раздел должен работать и без подробного личного профиля. Каждый медицинский факт обязан иметь проверяемый источник.
11. В onboarding для сигарет собрать приблизительный год начала регулярного курения или стаж; при наличии интенсивности допустимо рассчитывать pack-years как вспомогательный evidence-matching signal, но не превращать популяционные риски в персональный диагноз.
12. Lapse/эпизод курения ничего не обнуляет. Добавить context disruption: не усиливать старую связку, особенно `машина = сигарета`; никогда не рекомендовать курение за рулём. Если употребление уже происходит, допускается только наблюдение факта/эффекта без оптимизации курения.
13. Усилить Связки до implementation intention: `Если X → сначала Y`; предусмотреть будущие rescue plans по реальным повторяющимся сценариям.
14. Реализовать раздел основного меню `Вместе`: реальные групповые агрегаты, personal-baseline comparison, activity pulse, re-engagement без shame/competition, privacy whitelist и защита малых выборок. Никакого leaderboard и никакого private text.
15. Исправить утверждённый логотип окончательно через root-cause diagnosis: active entrypoint → asset → CSS → production bundle/runtime. Не менять и не перегенерировать бренд.
16. Все schema/data changes — только versioned migrations из repo. RLS и privacy-by-design обязательны.
17. Добавить/обновить release requirements, validation, rollback, changelog и AI audit trail.
18. Работать в отдельной ветке и закончить draft PR с handoff владельцу.

## Следующий этап после v3.1

Отдельно, не смешивая с этим release unit:

- спроектировать Admin / Product Intelligence;
- переделать application boundary так, чтобы Web, Telegram, native mobile и будущие клиенты работали через единые доменные/API-контракты поверх одной канонической базы;
- не дублировать business logic между клиентами;
- сохранить modular monolith и единый source of truth, пока измеренная нагрузка не потребует иного.

Эту архитектурную задачу нужно зафиксировать в roadmap как следующий этап и подробно спроектировать после завершения v3.1.
