# Product Backlog ALIVE

Этот файл — каноническая очередь продуктовых идей, которые владелец сформулировал, но которые ещё не стали обязательным scope конкретного release unit.

Backlog существует для того, чтобы **не ограничивать product vision владельца и одновременно не разрушать последовательность реализации**.

## Главное различие

- `releases/<release>/IMPLEMENTATION_PLAN.md` — что **обязательно делаем сейчас**;
- `docs/ROADMAP.md` — что **запланировано по этапам и gates**;
- `docs/PRODUCT_BACKLOG.md` — что **важно не потерять, но ещё не зафиксировано в конкретный этап**;
- `docs/ACTIVE_RELEASE.md` — какой release сейчас активен, насколько его scope зафиксирован и когда следующий backlog review.

Идея не должна попадать в текущий runtime scope только потому, что она появилась во время обсуждения текущего release.

## Правила для агента

1. Владелец может свободно формулировать новые идеи в любой момент, в том числе во время реализации текущего release.
2. Агент сам обязан определить, относится ли идея к текущему blocker, текущему scope, roadmap, backlog или research track.
3. Если идея не нужна для прохождения acceptance criteria текущего release, по умолчанию она **не расширяет текущий release**.
4. Такая идея сохраняется здесь либо сразу в roadmap, если её место и gate уже очевидны.
5. Агент не просит владельца повторять идею позднее: после записи в git ответственность за её сохранность лежит на проекте.
6. На каждом release gate агент обязан пересмотреть backlog и предложить: `PROMOTE / KEEP / RESEARCH / DROP`.
7. `PROMOTE` означает перенос идеи в roadmap или в новый release contract с явными acceptance criteria.
8. Нельзя тихо удалять идею. `DROP` требует краткой причины и, если идея была явно важна владельцу, owner decision.
9. Backlog не должен дублировать уже запланированный roadmap. После promotion здесь остаётся только короткая ссылка на новое каноническое место.
10. Backlog не используется как оправдание бесконечного scope: одновременно активен один основной user-facing release unit, если owner явно не принял иной режим.

## Статусы

- `INBOX` — идея записана, но ещё не разобрана.
- `TRIAGED` — смысл понятен, но этап не выбран.
- `READY` — достаточно определена, чтобы предложить её в следующий release.
- `RESEARCH` — сначала нужны данные/исследование/техническая проверка.
- `PROMOTED` — перенесена в roadmap/release contract.
- `DROPPED` — осознанно не реализуем; причина сохранена.

## Формат элемента

```md
### B-XXX — Короткое название

- status: INBOX | TRIAGED | READY | RESEARCH | PROMOTED | DROPPED
- added: YYYY-MM-DD
- source: owner | research | user-data | technical
- problem/value: какую проблему или ценность увидели
- idea: сама идея без преждевременного технического решения
- why-not-now: почему не входит в текущий release
- revisit-gate: после какого gate агент обязан вернуться к идее
- dependencies: если есть
- promoted-to: ссылка на roadmap/release, если PROMOTED
- decision-note: причина KEEP / RESEARCH / DROP / PROMOTE
```

## Текущий backlog

На момент создания этого файла отдельного неперенесённого product backlog нет: крупные идеи последних итераций уже распределены по текущему `4.0.0-alpha.1`, последующим этапам `4.x`, Product Evidence Gate и Later Support Track в `docs/ROADMAP.md`.

Это **не означает, что backlog закрыт**. Следующая новая идея владельца, не обязательная для активного release, должна быть записана сюда в момент её появления.

## Обязательный backlog review

Backlog review выполняется:

1. перед freeze нового release;
2. после PASS/FAIL ключевого gate текущего release;
3. после существенного нового research finding;
4. когда owner меняет приоритет продукта;
5. перед началом следующей пользовательской версии.

Результат review фиксируется в release plan/handoff и при необходимости обновляет `docs/ROADMAP.md`.

## Защита от двух крайностей

Нельзя:

- **душить vision** — откладывать обсуждение хорошей идеи только потому, что сейчас идёт другой release;
- **размывать delivery** — автоматически превращать каждую новую идею в изменение текущего release.

Правильный режим:

> **Свободно думать → всё сохранять → осознанно приоритизировать → замораживать маленький целостный scope → доводить его до доказуемого результата → возвращаться к backlog.**
