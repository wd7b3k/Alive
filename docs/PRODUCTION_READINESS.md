# ALIVE — готовность к полноценному проду

Дата: 2026-08-25. Ветка `feat/facts-polish`, коммит на момент составления — `5a94839`.

Документ описывает фактическое состояние, а не план. Каждый пункт проверен запросом к
базе, прогоном тестов или чтением кода; там, где проверить не удалось, это сказано прямо.
Решение «релиз выпущен» принимает владелец по `RELEASE_POLICY.md` — этот документ его не
принимает и не подменяет.

## 1. Что уже держится

- **Изоляция данных.** `supabase/tests/local` прогоняется на чистом Postgres 16 и
  проверяет: пользователь A не читает и не меняет ни одной строки пользователя B;
  анонимный посетитель читает опубликованные каталоги и ноль строк из 17 приватных
  таблиц; журнал событий закрыт политикой; список администраторов недоступен клиенту;
  сводка «Вместе» подавляет разбивку ниже порога когорты. Каждая из этих проверок
  проверена негативно — сломана намеренно, чтобы убедиться, что тест падает.
- **История миграций сведена.** 46 миграций в `supabase/migrations` применяются подряд
  на пустой базе без ошибок. До 25 августа этого не было: три ветки, из которых собран
  прод, в `main` не входили, а одна из их миграций вообще не применялась на чистой базе.
- **Аналитика пишется базой.** Триггеры `alive_record_*` фиксируют регистрацию, настройку,
  эпизод, действие внутри эпизода, употребление, чекин, цель и связку. Приложение
  добавляет только то, чего триггеры видеть не могут: открытие сценария тяги и уход из
  него на полпути.
- **Здоровье продукта** читается одним вызовом `admin_product_health`, возвращающим
  агрегаты без единого идентификатора. Доступ — по закрытому allowlist в схеме `private`.

## 2. Блокирует вывод в прод

### 2.1 Десять миграций никогда не применялись к базе

`supabase_migrations.schema_migrations` содержит 33 записи, последняя — `20260817210507`.
Всё, что появилось после, к проду не применялось: от `20260821120000` до `20260825150000`.
Готовый файл — `apply-to-prod-pending.sql`.

**Важно про способ применения.** Если прогнать этот файл через SQL Editor, база изменится,
но в `schema_migrations` не появится ни строки. Следующий `supabase db push` увидит эти
миграции как непримененные и попробует накатить их повторно — а среди них есть
`20260825140000`, которая удаляет колонки. Поэтому:

- либо применять через `supabase db push` (тогда учёт ведётся сам);
- либо, применив через редактор, дописать версии руками:
  `insert into supabase_migrations.schema_migrations(version) values ('20260821120000'), … ;`

Смешивать два способа без записи версий — это заготовка на будущий сбой, а не мелочь.

### 2.2 Нет интерфейса выгрузки и удаления аккаунта

`exportMyData` и `deleteMyAccount` написаны в `app/src/actions.ts` и не вызываются ни из
одного экрана — проверено поиском по `app/src`. Для продукта, который просит записывать
состояние в зависимости, «выгрузить своё» и «удалить себя» — не удобство, а условие
доверия. Пока кнопок нет, обещание в `PRIVACY_AND_DATA.md` не выполняется интерфейсом.

### 2.3 Домен не переключён

`INFRASTRUCTURE_STATE.md`: канонический хост — `https://alive.hmnos.ru`, фактический —
`https://alive-aw2.pages.dev`. В Supabase Auth Site URL и Redirect URL указывают на
`pages.dev`. Переключение — три согласованных действия: DNS и custom domain в Cloudflare
Pages, Site URL и Redirect URL в Supabase, обновление этого документа. Порядок важен:
смена Site URL раньше домена ломает вход.

### 2.4 Ротация ключей

Ключи Supabase выдавались инструментам, которым доступ больше не нужен. Пока `service_role`
не пересоздан, отзыв доступа неполон: ключ, однажды попавший в чужое окружение, остаётся
рабочим. Делается в Project Settings → API. Сделать это может только владелец.

## 3. Стоит сделать до прода, но не блокирует

- **Срок хранения событий.** `analytics_events` растёт без ограничения и без политики
  удаления. Для продукта о здоровье это вопрос не места на диске, а обещания: журнал
  поведения человека не должен храниться вечно по умолчанию. Нужна политика (например,
  события старше года удаляются) и строка о ней в `PRIVACY_AND_DATA.md`.
- **Резервные копии.** Проверить, включён ли PITR на тарифе проекта, и записать факт в
  `INFRASTRUCTURE_STATE.md`. Сейчас в репозитории об этом нет ничего.
- **Анонимная запись ошибок.** С `20260825150000` анонимный посетитель может добавить
  безымянную строку в `system_errors`. Это осознанный размен: без него поломки на
  публичных экранах не видит никто. Если появится мусор, ограничивать надо на шлюзе, а не
  отзывом гранта.
- **Backup-таблицы.** `20260824130000` и `20260825140000` оставляют в базе снимки
  каталогов (`*_backup_20260824`, `*_backup_20260825`). Они закрыты от клиента, но это
  временная страховка: после того как владелец примет новый текст, их надо удалить
  отдельной миграцией.
- **`awareness_content` не используется.** 18 карточек микроосознанности и 19 привязок к
  моментам лежат в базе, и ни один экран их не показывает. Либо вывести, либо
  зафиксировать как отложенное — но не оставлять молча.

## 4. Что проверяется только руками

Автоматика не покрывает вход через Google и реальный путь до PostgREST. Перед объявлением
релиза нужен прогон из `releases/v3.0-platform/VALIDATION.md`: два настоящих Google-аккаунта
на боевом развёртывании, каждый видит только свои данные, выгрузка и удаление работают.
Локальный набор тестов доказывает корректность политик на уровне SQL и не заменяет этого.
