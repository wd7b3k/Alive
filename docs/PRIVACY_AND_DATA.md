# Privacy и данные Habitoff

## 1. Принцип

Habitoff работает с данными, которые могут быть чувствительными: зависимое поведение,
срывы, триггеры, личные Смыслы, Связки и optional notes.

Поэтому базовая модель:

**минимум сбора + private by default + понятный consent + техническая изоляция.**

## 2. Некоммерческая модель данных

Habitoff не использует пользовательские данные для:

- рекламного таргетинга;
- продажи аудитории;
- передачи data brokers;
- построения маркетингового профиля для третьих сторон.

Если коммерческий статус проекта когда-либо изменится, эти принципы не меняются молча:
требуется отдельное privacy decision и новый consent.

**Как устроен consent (с 27.08.2026).** Галочка на экране входа: без неё кнопки
провайдеров выключены. Версия текста и дата пишутся в `profiles.consent_version` и
`consent_accepted_at`; проверка в схеме не даёт записать одно без другого. Версия строкой
означает, что при смене формулировки сравнение с текущей версией само покажет, у кого
согласие устарело, — требование «новый consent» выполняется без отдельной таблицы.
Решение — ADR-0006.

## 3. Где физически лежат данные

Записано 27.08.2026, до появления живых пользователей на новой инфраструктуре — намеренно
до, а не после.

| Что | Где |
|---|---|
| База с личными записями | один сервер Timeweb Cloud, зона Москва, Россия |
| Резервные копии на сервере | тот же диск, `/srv/alive/backups` |
| Вторая копия бэкапов | машина владельца, Россия |
| Идентификация при входе | Google (США) и Яндекс (Россия) — только факт входа и почта |
| Сертификат TLS | Let's Encrypt, США — доменное имя, без данных пользователей |

До 27.08.2026 база находилась в Ирландии (Supabase Cloud, `eu-west-1`), а статику отдавал
Cloudflare. Переезд убрал обоих из контура. Данные российских пользователей теперь в РФ,
что снимает вопрос 152-ФЗ в его основной части. Это не юридическая консультация, но факт
зафиксирован здесь намеренно: восстановить его потом по памяти будет нельзя.

Внешних сервисов в рантайме нет: ни CDN, ни аналитики по умолчанию, ни внешнего
мониторинга, ни объектного хранилища. Каждое исключение из этого правила — решение
владельца, которое должно появиться в этом документе.

## 4. Identity

- Вход через Google — встроенный провайдер;
- вход через Яндекс — собственный мост на этом же сервере
  (см. [`AUTH_PROVIDERS.md`](AUTH_PROVIDERS.md));
- провайдер используется только для идентификации;
- внутренние business entities связаны с собственным UUID;
- email не используется как primary foreign key.

Почтовый сервис не подключён: мост выпускает сессию без письма. Значит адрес почты никуда
не отправляется и используется только как идентификатор внутри базы.

## 5. Tenant isolation

Пользовательские таблицы защищаются PostgreSQL Row Level Security.

Frontend не может доверенно задавать чужой `user_id`.

Политика должна гарантировать, что participant не может читать/изменять private rows
другого participant. Проверяется двумя способами: локальным тестом на чистом Postgres и
живым запросом снаружи через боевой путь целиком.

## 6. Private content

По умолчанию private:

- Episodes;
- optional notes;
- пользовательские Смыслы;
- пользовательские Связки;
- NRT usage;
- food replacement history;
- детальные triggers/needs;
- текст контекста вне каталога (`episodes.custom_trigger_text`);
- индивидуальные settings;
- персональная recommendation history.

## 7. Страница «Вместе»

Группе разрешены только заранее определённые агрегаты.

Не показывать:

- notes;
- тексты Смыслов;
- тексты Связок;
- конкретные craving details;
- NRT;
- пищевые Замены;
- любые приватные тексты.

## 8. UGC

Пользовательский контент попадает в очередь общего каталога только после отдельного
действия: `Предложить в общую базу`.

Submission является отдельной копией/сущностью. Private original не становится публичным.

Желательно хранить отдельный `attribution_allowed`.

## 9. Admin

Админка по умолчанию работает на:

- агрегатах;
- event IDs/categories;
- anonymized/limited operational data;
- explicitly submitted UGC.

Админ не должен получать удобный «просмотр всей личной жизни пользователя» только потому,
что технически имеет service role.

Privileged access к private content, если когда-либо потребуется для incident support,
должен быть отдельным audited break-glass flow.

## 10. Аналитика и счётчики

Analytics events не должны содержать raw sensitive text. Хранить: event type,
IDs/categories, timestamps, latency/error metadata, coarse product context.

Правило действует и там, где текст человека стоит прямо рядом с событием. Контекст вне
каталога (ADR-0017, Р1) пишет в `analytics_events` событие `trigger_other_used` с кодом
причины `no_trigger_match` и флагом `text_given`; сам текст остаётся в эпизоде.
Проверяется это не договорённостью и не фильтром `sanitizeMetadata` — он выбрасывает
строки длиннее 64 знаков и от текста короче не спасает, — а тестом
`app/src/flow-other-trigger.test.tsx`, который ищет саму введённую строку во всех
ушедших событиях.

**Google Analytics на своей инфраструктуре не включается.** Он тянет
`googletagmanager.com` в браузере каждого посетителя, то есть внешний сервис в рантайме —
ровно то, из-за чего продукт уходил с чужой инфраструктуры. `VITE_GA_MEASUREMENT_ID`
оставлен пустым сознательно.

Яндекс Метрика доступна как вариант, но на 27.08.2026 тоже выключена. Если будет
включена, действуют два ограничения:

- **вебвизор выключен** — он записывает экран, а экран здесь это то, что человек пишет о
  своей зависимости. В коде `webvisor: false` стоит явно. Настройка «Записывать все поля:
  Откл» в кабинете вебвизор **не** выключает: она касается только содержимого полей
  ввода, а запись экрана продолжается;
- **счётчик не загружается на личных экранах.** Даже без текстов он сообщает третьей
  стороне, какие разделы человек открывает, а по разделам сервиса о никотиновой
  зависимости выводится слишком многое.

Если решение изменится, оно записывается здесь и в `SEO_AND_ANALYTICS.md`, а не делается
молча.

## 11. Удаление и выгрузка

Пользователь должен иметь возможность:

- удалить отдельный event;
- удалить собственный Смысл/Связку;
- экспортировать свои данные;
- удалить профиль.

Удаление профиля реализовано аутентифицированной edge-функцией
`supabase/functions/delete-account`, развёрнутой на своём сервере.

Soft delete допустим для event integrity только при понятной retention policy. Полное
удаление профиля должно иметь конечный purge path.

**Открытый вопрос:** `analytics_events` растёт без ограничения и без политики удаления.
Для продукта о здоровье это вопрос не места на диске, а обещания: журнал поведения
человека не должен храниться вечно по умолчанию. Нужна политика и строка о ней здесь.

## 12. Резервные копии

Бэкапы содержат те же чувствительные данные, что и база, и подчиняются тем же правилам.

- дампы лежат на сервере в РФ и в копии на машине владельца в РФ;
- резервные копии в панели провайдера выключены: копия на том же аккаунте не закрывает
  сценарий «аккаунт у провайдера недоступен», а лишний экземпляр личных данных создаёт;
- вместе с дампом сохраняется `.env` — без него база не поднимется, потому что там
  JWT-ключи. Значит архив бэкапа сам по себе является секретом и хранится соответственно;
- удаление аккаунта не удаляет его из уже снятых бэкапов. Срок хранения копий — четырнадцать
  дней на сервере — и есть верхняя граница этого хвоста, и это надо честно писать на
  публичной privacy-странице.

## 13. Секреты

Запрещено в git/frontend/logs:

- `service_role` / secret key;
- OAuth secrets Google и Яндекса;
- токены почтовых провайдеров;
- реальные private health/behavioural exports;
- access tokens;
- пароли базы.

`app/.env` находится в `.gitignore` — на self-hosted там лежат ключи, а не только адрес
проекта. Скан собранного бандла на секреты — постоянный шаг CI.

## 14. Инфраструктурные поставщики

Публичная privacy-страница должна честно объяснять: абсолютной изоляции от
infrastructure providers не существует.

**Резервные копии на 27.08.2026 ещё не настроены.** До появления живых участников это
блокирующий пункт, а не задача из бэклога: см. `docs/ROLLOUT.md` §5.

После переезда список короче, чем был, но он не пуст: Timeweb Cloud (сервер и его
физический доступ к дискам), Google и Яндекс (вход), Let's Encrypt (сертификат), Рег.ру
(DNS). Каждый из них может обрабатывать технические данные по своим правилам.

Habitoff не должен обещать «мы вообще никому ничего не передаём», если это технически
неверно. Правильная формулировка — «личные записи не покидают наш сервер в России», а не
«третьих сторон нет».

## 15. Privacy language

Допустим прямой человеческий тон:

> Эти данные слишком личные, чтобы превращать их в рекламный профиль.

Но нельзя делать ложные абсолютные заявления о безопасности или противопоставлять себя
другим компаниям так, будто third-party infrastructure отсутствует.

## 16. Security gates

До подключения внешних участников должны пройти минимум:

- RLS isolation tests, локальные и снаружи;
- participant vs admin authorization tests;
- frontend secret scan;
- data export/delete tests;
- Together whitelist tests;
- UGC consent tests;
- проверка периметра снаружи: открыты ровно 22, 80, 443;
- проверенное восстановление из резервной копии.
