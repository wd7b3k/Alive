# Способы входа

На 27.08.2026 работают два: Google и Яндекс. Оба проверены живым входом на
`https://habitoff.ru`.

Документ переписан после переезда на self-hosted Supabase. Прежняя редакция описывала
настройку кастомного провайдера через панель Supabase Cloud — на своём сервере этот путь
не существует, и дело не в настройке.

## Как экран входа решает, что показать

Список кнопок задаётся переменной сборки:

```env
VITE_AUTH_PROVIDERS=google,yandex
```

Первый в списке — главная кнопка. Раньше список спрашивался у самого Supabase через
`GET /auth/v1/settings`, и это было правильно для облака: включил провайдера в панели —
кнопка появилась. На self-hosted это перестало работать, потому что Яндекса в ответе не
будет никогда — его там физически нет (см. ниже). Опрос `/auth/v1/settings` в коде
остался и продолжает работать для встроенных провайдеров, но переменная его перебивает,
и на проде используется именно она.

Следствие, которое надо помнить: **новый способ входа теперь требует пересборки**, а не
только настройки на сервере.

## Google — настройкой

Переменные живут в `docker-compose.override.yml` на сервере, значения — в `.env`:

```
GOTRUE_EXTERNAL_GOOGLE_ENABLED
GOTRUE_EXTERNAL_GOOGLE_CLIENT_ID
GOTRUE_EXTERNAL_GOOGLE_SECRET
GOTRUE_EXTERNAL_GOOGLE_REDIRECT_URI   = ${API_EXTERNAL_URL}/callback
```

`API_EXTERNAL_URL` равен `https://habitoff.ru/auth/v1`, поэтому redirect собирается как
`https://habitoff.ru/auth/v1/callback`. Этот адрес должен быть добавлен в Google Cloud
Console → Credentials → OAuth 2.0 Client ID → Authorized redirect URIs.

Используется та же пара client_id/secret, что и на облачном проекте: тогда люди, уже
входившие через Google, остаются для Google теми же людьми. Старый redirect URI не
удаляется, пока облачный проект не выведен окончательно.

## Яндекс — собственный мост

### Почему настройкой нельзя

Две независимые причины, каждой достаточно.

**В self-hosted GoTrue список внешних провайдеров фиксирован**, и Яндекса в нём нет.
Механизма «custom provider», который был в облачной панели, здесь не существует.

**GoTrue ищет стандартный OIDC-claim `email`, а Яндекс его не отдаёт.** Проверено
26.08.2026 на облачном проекте, где `custom:yandex` был настроен: согласие Яндекса
выдаётся, обратно приходит
`error_code=unexpected_failure&error_description=Error+getting+user+email+from+external+provider`.
GoTrue выдаёт эту ошибку, когда профиль получен, а поле почты пусто.
`https://login.yandex.ru/info?format=json` возвращает `default_email` и массив `emails`;
поле `email` появляется только в формате `format=jwt`. Версия «не выданы права» проверена
и отпала: в кабинете приложения запрошены и почта, и имя. Значит Яндекс почту отдаёт, а
GoTrue её не видит — остаётся несовпадение имён полей, и настройкой оно не лечится ни в
облаке, ни на своём сервере.

### Как устроен мост

Код: `supabase/functions/yandex/index.ts`. Живёт в том же edge-runtime, который уже
развёрнут ради удаления аккаунта, — ничего нового снаружи не появляется.

**`GET /functions/v1/yandex/start`** генерирует `state`, кладёт его в httpOnly-cookie и
редиректит на `https://oauth.yandex.ru/authorize`.

**`GET /functions/v1/yandex/callback`** сверяет `state`, меняет код на токен через
`POST https://oauth.yandex.ru/token`, затем берёт профиль
`GET https://login.yandex.ru/info?format=json` с заголовком **`Authorization: OAuth <token>`**
— именно `OAuth`, как в документации Яндекса, а не `Bearer`. Старый вопрос про заголовок
здесь закрыт окончательно: заголовок наш.

По `id` и `default_email` мост находит или создаёт пользователя через админский API
GoTrue (`/admin/users`, ключ `service_role`, только внутри docker-сети), затем выпускает
сессию через `POST /admin/generate_link` с `type: "magiclink"` и возвращает человека в
приложение с одноразовым `token_hash` **во фрагменте** адреса. Клиент вызывает
`supabase.auth.verifyOtp({ type: 'magiclink', token_hash })` и получает обычную сессию.

**Письмо при этом не отправляется, поэтому SMTP не нужен вовсе.** Зафиксировано явно.

### Требования безопасности — не опциональные

- `state` обязателен: без сверки это дыра в CSRF;
- `service_role` существует только внутри контейнера и в браузер не попадает никогда;
- `token_hash` одноразовый, короткоживущий, уходит во фрагменте — он не попадает ни в
  логи веб-сервера, ни в заголовок `Referer` — и вычищается из адресной строки клиентом
  сразу, независимо от того, удался обмен или нет;
- мост доступен только через Caddy по HTTPS, напрямую наружу — нет.

### Две вещи, без которых мост не работает

**Caddy подставляет заголовок `apikey` для `/functions/v1/yandex/*`.** Шлюз Supabase
требует его на всех путях, а браузер при переходе по ссылке заголовков не шлёт — и
Яндекс, возвращая человека на `callback`, тем более. Без подстановки и кнопка, и возврат
упирались бы в 401. Ключ публичный по замыслу, поэтому лежит прямо в `Caddyfile`; при
перегенерации ключей его надо обновить и там.

**Redirect URI в кабинете приложения Яндекса** — `https://habitoff.ru/functions/v1/yandex/callback`,
а не `/auth/v1/callback`: Яндекс теперь общается не с GoTrue, а с мостом.

Права приложения: «Адрес электронной почты», «Имя пользователя, ссылка на портрет».

### Что делать, если вход сломается

Мост возвращает человека в приложение с `?auth_error=yandex_<шаг>`. Суффикс указывает,
где именно оборвалось: `state`, `token`, `profile`, `no_email`, `create`, `link`,
`no_hash`. Если в адресной строке остался висеть `#token_hash=`, значит мост отработал,
а обмен на сессию на клиенте не удался — смотреть консоль браузера.

## VK ID и Mail.ru — отдельная работа, не настройка

VK ID (и Mail.ru, который в него переведён) работает по OAuth 2.1: PKCE обязателен, а
при обмене кода на токен требуется дополнительный параметр `device_id`.

После появления моста Яндекса путь для них понятен и повторим: та же схема, другая
функция. Это по-прежнему не настройка, а код, который держит в руках пользовательские
токены, и делать его надо отдельным release unit с собственными проверками.

Пока этого нет, честнее не показывать кнопку VK, чем показывать неработающую.

## Проверка перед тем, как объявлять способ входа рабочим

1. Вход в приватном окне с аккаунта, которого ещё нет в базе.
2. `auth.users` получил строку; для моста — с меткой провайдера в `raw_user_meta_data`.
3. `profiles` получил строку: `display_name` не пустой, `role` = `participant`.
4. `user_settings` создан.
5. Повторный вход тем же аккаунтом не создаёт второй профиль.
6. Выход и вход другим способом с той же почтой — проверить, склеились аккаунты или
   получились два. Это надо увидеть, а не предположить.
