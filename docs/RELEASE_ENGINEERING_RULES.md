# ALIVE — правила безопасной разработки и релизов

Статус: **канонический обязательный контракт для AI, Codex и разработчиков**

Этот документ существует потому, что v3.1 допустил недопустимую регрессию: вместо расширения утверждённого `RedesignApp` был создан параллельный root shell. Такой класс ошибок должен предотвращаться процессом и CI, а не только внимательностью исполнителя.

## 1. Основной принцип

> **Новый релиз ALIVE расширяет существующий продукт, а не пересобирает его заново**

По умолчанию любой релиз является additive

Новый функционал встраивается в существующие:

- domain/data contracts
- `RedesignApp`
- визуальные паттерны `r-*`
- навигационную иерархию
- пользовательские сценарии

Замена существующего слоя допускается только после отдельного owner gate с объяснением, зачем additive-подход объективно невозможен

## 2. Перед первой строкой кода

Исполнитель обязан восстановить контекст в следующем порядке:

1. `AGENTS.md`
2. `docs/CURRENT_STATE.md`
3. `docs/BRANDBOOK.md`
4. `docs/PRODUCT_PRINCIPLES.md`
5. `docs/PRODUCT_STRATEGY.md`
6. `docs/METHODOLOGY.md`
7. `docs/DATA_MODEL.md`
8. `docs/ROADMAP.md`
9. документация текущего release unit
10. последний релевантный `docs/ai_sessions/**/**-response.md`
11. diff последнего принятого UI-релиза
12. только после этого код

Для UI-задачи обязательно посмотреть текущий production-approved интерфейс или его актуальные screenshots/reference, а не делать вывод о дизайне только по JSX/CSS

## 3. Baseline inventory обязателен

Перед реализацией release unit создать или обновить список:

### Сохраняется без изменений

Функции и визуальные зоны, которые задача не просит менять

### Изменяется

Только элементы, прямо относящиеся к требованиям release

### Добавляется

Новые функции и маршруты

### Удаляется

По умолчанию **ничего**

Любое удаление существующей возможности должно быть перечислено явно и согласовано владельцем

Фраза «новая реализация всё равно покрывает этот сценарий» не является разрешением удалить старую функцию

## 4. Root shell freeze

Без отдельного owner gate запрещено:

- менять `RedesignApp` на другой root component
- переключать `main.tsx` на новый shell
- создавать `V32App`, `NewApp`, `NextShell` и аналог как новый корень продукта
- создавать вторую глобальную дизайн-систему
- подключать глобальный CSS, который переопределяет базовые `r-*` surfaces/palette/type system
- переписывать Header/Today/navigation целиком ради локальной функции

CI обязан контролировать этот контракт через `app/scripts/check-ui-contract.mjs`

## 5. Diff budget

Перед крупной реализацией исполнитель обязан ответить:

- какие существующие файлы действительно необходимо изменить
- почему нельзя решить задачу меньшим diff
- какие существующие компоненты переиспользуются

Если новая функция требует сотни строк нового shell/UI до изменения существующего компонента — это сигнал остановиться и пересмотреть архитектуру

Для обычного feature-release предпочтительны небольшие целевые изменения вместо параллельного приложения

## 6. Одна ось изменений за проход

Интеграция крупного релиза выполняется вертикальными срезами

Пример для v3.1:

1. CTA и copy
2. guided flow progress/back-navigation
3. Replacement ranking
4. Myths contextual reminder
5. Facts section
6. Together section
7. onboarding exposure metadata
8. lapse improvements

После каждого среза:

- typecheck
- build
- UI-contract
- smoke-test релевантного сценария
- проверка, что baseline-функции не исчезли

Не объединять новый shell + новый IA + новые данные + новый визуальный язык в один проход

## 7. Regression matrix

Каждый UI-релиз должен проверить минимум:

- Google login
- Сегодня
- главный craving CTA
- guided flow от начала до сохранения
- возврат на предыдущие шаги, если существует
- быстрая запись никотина
- удаление ошибочного события и пересчёт
- вечерний разбор
- Связки
- пользовательские Связки CRUD
- Путь
- Смыслы
- пользовательские Смыслы CRUD
- профиль / изменение baseline
- методологию
- logout
- mobile bottom navigation
- logo desktop/mobile/login

Добавление новой функции расширяет эту матрицу, но не сокращает её

## 8. CI — необходим, но недостаточен

PASS следующих проверок не означает release-ready сам по себе:

- TypeScript
- Vite build
- SQL migration
- RLS test
- unit tests

Обязательны также:

- `UI CONTRACT — PASS`
- реальный browser smoke-test
- desktop visual review
- mobile visual review
- owner visual gate для заметного UI-изменения

`build PASS + owner говорит «интерфейс сломан» = release FAIL`

## 9. Сравнение до/после

Перед owner review исполнитель должен предоставить один и тот же набор экранов в предыдущем и новом состоянии либо убедиться визуально по реальному preview

Критерий:

> Если функция не была объектом задачи, пользователь не должен задаваться вопросом «почему это теперь выглядит/работает иначе»

## 10. Работа с историей

Git используется как память продукта

Перед реализацией похожего сценария:

- найти последний commit/PR, где он работал
- прочитать rationale
- проверить release validation
- переиспользовать существующую реализацию

Запрещено реализовывать существующую функцию заново только потому, что это быстрее в моменте

## 11. Database-first не означает UI rewrite

Новая схема БД или API не требует нового клиентского shell

Сначала сделать backward-compatible data adapter

Затем подключить его к существующему UI

Если новый backend contract ломает текущий клиент, предпочтительнее adapter/versioned API, а не переписывание клиента

Это особенно важно перед multi-client архитектурой Web / Telegram / mobile

## 12. Ветка и релиз

Каждая значимая работа:

- отдельная ветка
- release unit
- prompt/response audit trail
- requirements
- validation
- rollback
- draft PR до owner gate

Нельзя merge автоматически только потому, что CI зелёный

## 13. Правило трёх подтверждений

Перед merge UI-релиза должны одновременно существовать:

1. **Техническое подтверждение** — CI/tests/build
2. **Функциональное подтверждение** — regression matrix
3. **Визуальное подтверждение** — реальный preview и owner gate при существенном UI

Отсутствие любого из трёх = release остаётся draft

## 14. Если возникла неопределённость

Если исполнитель не уверен, является ли изменение локальным feature или redesign:

- считать его redesign
- не выполнять без owner gate

Если не уверен, можно ли удалить/заменить существующую механику:

- сохранить её

Если новый подход конфликтует с Brandbook:

- Brandbook имеет приоритет до явного решения владельца

## 15. Postmortem rule

Каждая обнаруженная владельцем серьёзная регрессия должна привести минимум к одному системному изменению:

- CI guard
- test
- contract
- checklist
- architecture rule

Недостаточно просто «исправить конкретный экран»

## 16. Определение хорошего релиза ALIVE

Хороший релиз ощущается так:

> Вчерашний ALIVE всё ещё здесь, просто теперь он умеет больше и делает нужное точнее

Плохой релиз ощущается так:

> Это как будто другое приложение, в котором заново попытались реализовать то, что уже работало

Второй вариант является регрессией независимо от количества нового функционала
