# Релизная политика Habitoff

Этот документ — единственное подробное описание того, как изменения попадают на прод.
`AGENTS.md` на него ссылается и не дублирует: два описания одного правила расходятся
быстрее, чем описание расходится с кодом.

## 1. Каноническая история

- v2.7 — последняя legacy production reference;
- v2.8 не является production release;
- новая продуктовая серия начинается с v3.0.

Экспериментальные локальные архивы не становятся релизами только потому, что получили
имя ZIP.

## 2. Release unit

Каждое значимое изменение оформляется как отдельный release unit с:

- scope;
- changed files/modules;
- schema/methodology changes;
- validation;
- privacy/security checks;
- rollback;
- known limitations;
- release notes.

## 3. SemVer-like дисциплина

На раннем этапе:

- `3.0` — platform/core-loop milestone;
- `3.1` — Together milestone;
- `3.2` — Admin/Intelligence milestone;
- patch version (`3.0.1`) допускается только для фактически выпущенного `3.0`.

Нельзя создавать `3.0.1`, если `3.0` не был принят/выпущен.

## 4. Документация релиза

Минимум:

- `README.md`;
- `RELEASE_NOTES.md`;
- `VALIDATION.md`;
- `ROLLBACK.md`;
- `INTEGRITY.md` при downloadable artifact;
- `MIGRATION.md` при schema/data migration;
- обновление `CURRENT_STATE.md`.

Для v3 platform дополнительно:

- `ARCHITECTURE.md`;
- `DB_SCHEMA.md`;
- ссылка на канонический privacy contract;
- `TEST_REPORT.md`.

## 5. Как изменение попадает на прод

Прод — один сервер, собирается **только с `main`**.

```bash
cd /srv/alive/repo && git checkout main && git pull && /srv/alive/deploy.sh
```

`deploy.sh` делает ровно это, по порядку:

1. **отказывает, если рабочее дерево git не чистое** — физический запрет выложить то,
   чего нет в коммите;
2. **отказывает, если число файлов миграций не равно числу записей в
   `supabase_migrations.schema_migrations`** — расхождение репозитория и прода ловит
   машина, а не глаза через месяц;
3. `npm ci && npm run build`;
4. кладёт сборку в `/srv/alive/releases/<дата-время>`, удаляет оттуда sourcemap;
5. атомарно переключает симлинк `current` (`mv -Tf` поверх симлинка: момента, когда
   `current` не существует, не бывает);
6. оставляет на диске пять последних сборок.

Оба гейта — не формальность, а защита ровно от того класса расхождений, который в этом
проекте уже случался четыре раза.

### 5.1. Сверка «main ⇄ прод»

`deploy.sh` защищает от выкладки того, чего нет в коммите. Он ничего не знает о том,
что выкладку **вообще не запустили**. Этот случай в проекте и происходил: 27.08.2026
`habitoff.ru` отдавал заголовок «ALIVE», хотя ребрендинг сутки лежал в `main`.

Поэтому каждая сборка подписана коммитом, а прод отдаёт его машинно:

```bash
node scripts/check-deploy-drift.mjs          # против https://habitoff.ru
curl -s https://habitoff.ru/version.json     # то же самое глазами
```

Совпало — команда молчит. Не совпало — печатает, на сколько коммитов и на какие именно
прод отстал, и выходит ненулевым кодом. Расхождение старше суток считается сигналом.

Тот же отпечаток виден человеку внизу страницы `/releases`. Решение —
[`decisions/ADR-0009-deploy-drift-detection.md`](decisions/ADR-0009-deploy-drift-detection.md).

## 6. Откат

**Статика — одна строка**, потому что предыдущие сборки лежат рядом:

```bash
ln -sfn /srv/alive/releases/<предыдущая> /srv/alive/current.new
mv -Tf /srv/alive/current.new /srv/alive/current
```

**Миграции откату не подлежат.** Симлинк возвращает статику, но не схему. Отсюда
требование к каждой миграции: она должна быть безопасна на живых данных. `add column` с
дефолтом — да. `drop column` в том же релизе, что и код, переставший им пользоваться, —
нет: это разносится на два релиза.

Единственный путь назад по схеме — восстановление из бэкапа, поэтому бэкап должен
существовать и быть проверенным до, а не после.

## 7. Изменения базы

Все migrations versioned в git. Запрещено:

- вручную менять схему или контент прода без migration record;
- silent reinterpretation historical data;
- destructive migration без backup/rollback.

Порядок применения: **сначала на базе, поднятой с нуля, потом на боевой.** Всегда.
Команды и оговорка про то, почему одноразовой базой не может быть голый образ
`supabase/postgres`, — в `supabase/README.md`.

Запись версии в `supabase_migrations.schema_migrations` — обязательная часть применения,
а не бухгалтерия: миграция, применённая без записи, однажды накатится повторно.

## 8. Изменения edge-функций

Код живёт в `supabase/functions/` репозитория. На сервер синхронизируется:

```bash
rsync -a /srv/alive/repo/supabase/functions/ /srv/supabase/volumes/functions/
cd /srv/supabase && docker compose restart functions
```

Править файлы прямо в `/srv/supabase/volumes/functions/` запрещено: через месяц никто не
вспомнит, откуда там взялся код.

## 9. Изменения конфигурации сервера

`docker-compose.override.yml`, `Caddyfile` и состав переменных окружения — часть
инфраструктуры и отражаются в `docs/INFRASTRUCTURE_STATE.md` в том же коммите, что и само
изменение. Значения секретов — нет.

Отдельно: переменные `VITE_*` подставляются **на этапе сборки**. Изменение любой из них
требует пересборки и новой выкладки, само по себе оно ничего не меняет.

## 10. Изменения методологии

Изменения, меняющие смысл метрик/модели:

- новая methodology/equivalence version;
- release note;
- пересчёт derived projections допустим;
- raw data не переписывается.

## 11. Brand assets

Утверждённый логотип считается immutable asset между релизами, если владелец явно не
запросил изменение.

**2026-08-26 — исключение применено.** Владелец запросил смену бренда прямым текстом;
Om выведен из проекта, знак заменён вектором. Решение и его последствия —
`docs/decisions/ADR-0003-rebrand.md`. Правило не отменено: следующая замена знака
потребует такого же явного запроса и такой же записи решением.

## 12. Release gate

Нельзя считать релиз готовым только по syntax check. Минимально проверять:

- functional acceptance;
- privacy/tenant isolation — включая проверку снаружи, через боевой путь целиком;
- critical data integrity;
- responsive UI;
- отсутствие секретов в бандле;
- оба способа входа отработали на боевом домене;
- удаление аккаунта работает;
- documentation consistency;
- восстановление из бэкапа проверено;
- `reboot` поднимает стек без рук.

Последние два появились вместе со своим сервером: раньше за них отвечал провайдер.

## 13. AI-generated releases

AI не должен самостоятельно повышать версию или объявлять production deployment
состоявшимся без фактического подтверждения.

## 14. Scope freeze и structural debt

- после фиксации release scope новые продуктовые идеи уходят в backlog;
- release scope не расширяется без явного решения владельца и обновления requirements;
- stabilization и structural debt предыдущего release unit закрываются до начала новых
  функций;
- временные рабочие копии не являются release artifacts;
- preview-развёртывания на своей инфраструктуре отсутствуют: ветка больше не получает URL
  сама. Смотреть ветку через `npm run dev` на сервере и SSH-туннель
  (`ssh -L 5173:127.0.0.1:5173`). Порт наружу не открывается.
