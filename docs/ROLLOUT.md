Как довести работу из ветки до `https://habitoff.ru`. Составлено 27.08.2026 по живому
состоянию сервера.

Состояние инфраструктуры — `docs/INFRASTRUCTURE_STATE.md`. Правила релиза —
`docs/RELEASE_POLICY.md`. Что именно сейчас в ветках — `docs/CURRENT_STATE.md`.

## 3. Порядок

Порядок обязателен. Каждый шаг проверяется до следующего.

### 3.1. Запушить ветку

Сделано 27.08.2026: обе ветки на `origin`, `redesign/habitoff-system` → `e87e02e`,
`feat/pilot-readiness` → `4020f25`.

```
cd C:\Users\ПК\Projects\alive\Alive
git push -u origin redesign/habitoff-system
git push -u origin feat/pilot-readiness
```

**Следующий незакрытый шаг — 3.2.** `chore/vps-deploy` на GitHub нет: она живёт только в
`/srv/alive/repo`. Пока это так, `main` не может стать источником истины для прода, и
свести ветки негде, кроме сервера. Первое действие — запушить её:

```
cd /srv/alive/repo && git push -u origin chore/vps-deploy
```

### 3.2. Свести с веткой сервера

`chore/vps-deploy` и `redesign/habitoff-system` правят **один и тот же файл** —
`app/src/redesign/shared.tsx`, и обе — в компоненте `LoginPage`. Конфликт будет, и
разрешать его надо руками, а не `--theirs`:

| Что правит ветка сервера | Что правит ветка редизайна | Как свести |
|---|---|---|
| `BRIDGED` — Яндекс уходит на собственный мост вместо `signInWithOAuth` | разметка кнопок провайдеров: `.r-provider`, знак, подпись | **оба нужны.** Мост живёт в `start()`, знаки — в разметке. Пересечения по смыслу нет, только по строкам |
| `VITE_AUTH_PROVIDERS=google,yandex` в окружении сборки | `providerTile()` и `ProviderMark` понимают и `yandex`, и `custom:yandex` | ничего делать не нужно, проверено обоими идентификаторами |
| `consumeBridgeToken` в `useBootstrapSession.ts` | не трогается | берётся как есть |
| `.gitignore` | не трогается | берётся как есть |

Порядок сведения: сначала влить `chore/vps-deploy` в `main`, потом
`redesign/habitoff-system` в `main`, конфликт разрешить в `main` — тогда он
разрешается один раз и остаётся в истории.

### 3.3. Прогнать проверки на сведённом `main`


Отдельно — вёрстка. Поэлементный прогон на ширинах 320…1600 с шагом 20; признак
`documentElement.scrollWidth − clientWidth` для этого **не годится**, он возвращает ноль
там, где переполнение съедено обрезкой у предка. Метод — в `docs/DESIGN_SYSTEM.md` §9.

### 3.4. Выложить

На сервере:

```
cd /srv/alive/repo && git fetch && git checkout main && git pull
/srv/alive/deploy.sh
```

`deploy.sh` держит два гейта и падает, если хоть один не прошёл:

1. дерево git чистое;
2. число файлов миграций равно числу записей в `supabase_migrations.schema_migrations`.

**Второй гейт упадёт на этой раскатке, и это правильно.** В ветке пять новых файлов
миграций, а в базе прода их ещё нет: 50 против 45. Гейт существует ровно для того, чтобы
не выложить фронт, который ждёт колонок, которых в базе нет.

Порядок поэтому такой: **сначала миграции, потом сборка.** На сервере, до `deploy.sh`:

```
cd /srv/alive/repo && git pull
for f in supabase/migrations/20260827*.sql; do
  docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 < "$f" || break
done
```

Каждая из пяти идемпотентна (`add column if not exists`, `drop constraint if exists`,
`create or replace`), так что повторный прогон безопасен. Переименование контента в конце
проверяет само себя и падает с внятным сообщением, если в читаемом тексте осталось старое
имя.

После этого счётчики сходятся, и `deploy.sh` проходит.

Дальше — сборка, атомарное переключение симлинка `current`, пять последних сборок
остаются на диске.

Если менялись Edge Functions (в этой раскатке — нет):

```
rsync -a /srv/alive/repo/supabase/functions/ /srv/supabase/volumes/functions/
cd /srv/supabase && docker compose restart functions
```

### 3.6. Откат

Симлинк `current` переключается на предыдущую сборку — они лежат рядом, пять штук.

Базу откатывать не нужно и не следует: все пять миграций этой раскатки — добавления
колонок, расширение проверки и новая функция. Предыдущая сборка на новой схеме работает
без изменений, потому что ничего из того, чем она пользовалась, не удалено и не сужено.
Обратный путь есть только у переименования контента — и он не нужен: старое имя
возвращать некуда.

`supabase/tests/local/run.sh` — **RLS isolation: ALL PASS**.

### Чего в раскатке нет

- **Новых зависимостей.** Знаки провайдеров — вектор в коде, без сетевых запросов.
- **Изменений в правах доступа.** RLS и Edge Function удаления данных не тронуты;
  новая функция метрик закрыта тем же гейтом, что сводка здоровья.
- **Счётчиков.** `VITE_GA_MEASUREMENT_ID` пуст, Метрика выключена. Так и остаётся —
  `PROJECT_CHARTER.md` §2.

## 5. Что делать до появления живых пользователей

Порядок по убыванию цены ошибки:

1. **Бэкапы.** `pg_dump` по таймеру и тяга к себе по SSH. Восстановление проверить на
   пустом контейнере **до** переноса данных, а не после. Это единственный оставшийся
   блокирующий пункт перед тем, как звать первых участников.
2. **Перенос пользователей** из Supabase Cloud: `--data-only`, каталоги не трогать,
   сверка агрегатными SHA-256, проверка RLS после переноса.
3. **`infra/` в репозитории**: `docker-compose.yml`, `docker-compose.override.yml`,
   `Caddyfile` с зафиксированными версиями образов. Сейчас конфигурация сервера
   существует только на сервере.
4. **Наблюдаемость**: `alive-health.sh` по таймеру, `OnFailure` в юните.
5. **Проверка `reboot`** — стек должен подниматься сам.
6. ~~**`PRIVACY_AND_DATA.md`**: где физически лежат данные.~~ Сделано 27.08: §12 называет
   Timeweb Cloud в Москве и self-hosted Supabase, Cloudflare из схемы убран. Раздел про

## 7. Дальнейшее развитие

Правила, которые не должны потеряться между релизами:

- **Цвет** добавляется только через ADR. Список мест наблюдения закрыт тестом; шестое
  роняет сборку намеренно — `docs/BRANDBOOK.md` §6.
- **Размеры** берутся из трёх шкал. Первое значение вне шкалы роняет сборку.
- **Экран** документируется в `docs/SCREENS.md` в том же коммите, что и код. Экран без
  раздела считается недоделанным.
- **Расхождение с сервером** оформляется по Drift rule в `INFRASTRUCTURE_STATE.md`:
  сначала в репозиторий, потом на сервер. Ручная правка на сервере новой нормой не
  становится.
- **Проверка перед показом** — не «прогнал и цифра ноль», а «открыл скриншот и
  посмотрел». Оба раза, когда это правило нарушалось, работа возвращалась на переделку.
