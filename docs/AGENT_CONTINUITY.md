# Протокол продолжения ALIVE другим агентом

Цель документа — сделать разработку ALIVE независимой от памяти конкретного чата, конкретной модели и конкретного исполнителя.

Новый агент должен суметь восстановить проект из git и продолжить работу без пересказа истории владельцем.

Отдельная цель этого протокола — сохранить естественный стиль работы владельца: свободно развивать product vision по ходу обсуждения, **не превращая каждую новую идею в незапланированное расширение текущего release**.

## 1. Что считать истиной

Приоритет источников:

1. актуальный код и migrations в репозитории;
2. `docs/CURRENT_STATE.md`;
3. `docs/ACTIVE_RELEASE.md`;
4. принятые решения в `docs/decisions/`;
5. продуктовая и техническая стратегия;
6. документация текущего release unit;
7. `docs/PRODUCT_BACKLOG.md` и `docs/ROADMAP.md`;
8. AI audit trail;
9. только затем — внешний чат или устные пояснения.

Если документы противоречат друг другу, работу не продолжать на догадке. Зафиксировать конфликт и определить более новый/канонический источник.

## 2. Обязательная последовательность восстановления контекста

Перед значимой задачей прочитать:

1. `README.md`;
2. `AGENTS.md`;
3. `docs/CURRENT_STATE.md`;
4. `docs/ACTIVE_RELEASE.md`;
5. `docs/PROJECT_EVOLUTION.md`;
6. `docs/PROJECT_CHARTER.md`;
7. `docs/PRODUCT_STRATEGY.md`;
8. `docs/TECHNICAL_STRATEGY.md`;
9. `docs/DEVELOPMENT_RULES.md`;
10. `docs/AGENT_CONTINUITY.md`;
11. `docs/PRODUCT_BACKLOG.md`;
12. `docs/DESIGN_RESEARCH_AND_REQUIREMENTS.md`, если задача затрагивает UX/UI;
13. `docs/RESEARCH_MONITORING.md`, если задача затрагивает evidence/конкурентов;
14. `docs/METHODOLOGY.md`;
15. `docs/PRODUCT_PRINCIPLES.md`;
16. `docs/DATA_MODEL.md`;
17. `docs/ARCHITECTURE.md`;
18. `docs/PRIVACY_AND_DATA.md`;
19. `docs/HYPOTHESES_AND_METRICS.md`;
20. `docs/ROADMAP.md`;
21. релевантные ADR в `docs/decisions/`;
22. документацию текущего `releases/<release>/`;
23. последние релевантные `docs/ai_sessions/**/**-response.md`;
24. только после этого читать код затрагиваемых модулей.

## 3. Перед началом работы агент обязан определить

- текущую base branch;
- текущую рабочую branch;
- открытый PR;
- фактически принятый release baseline;
- активный release contract и его freeze state;
- какие gates уже пройдены;
- какие проверки не выполнялись;
- какие owner decisions требуются;
- какие данные нельзя потерять;
- какие интерфейсы/таблицы/модули затрагивает задача;
- какие новые идеи уже находятся в backlog/roadmap и не должны случайно попасть в текущий scope.

Нельзя считать draft PR принятым состоянием main.

## 4. Формат любого значимого handoff

Перед завершением работы агент оставляет в git handoff, из которого понятны:

### Сделано

- файлы;
- миграции;
- пользовательское поведение;
- аналитика;
- документация.

### Почему

- проблема;
- гипотеза;
- evidence или данные;
- связанное решение владельца.

### Проверено

Каждый пункт отдельно:

- `PASS`;
- `FAIL`;
- `НЕ ПРОВЕРЕНО`.

Нельзя объединять непроверенные пункты в формулировку «всё работает».

### Не сделано

Явный список оставшихся частей scope.

### Риски

- продуктовые;
- данные;
- privacy/security;
- технические;
- evidence/content.

### Backlog / roadmap changes

- какие новые идеи появились во время работы;
- куда они классифицированы;
- какие элементы backlog нужно пересмотреть на следующем gate.

### Следующий логичный шаг

Одна или несколько задач в порядке приоритета с объяснением зависимости.

Если текущий release близок к закрытию, handoff должен также предложить следующий freeze candidate.

## 5. Где сохранять handoff

Для каждого release unit:

- `releases/<release>/README.md` — смысл и scope;
- `releases/<release>/REQUIREMENTS.md` — требования;
- `releases/<release>/VALIDATION.md` — проверки;
- `releases/<release>/ROLLBACK.md` — возврат/forward-fix;
- при необходимости `releases/<release>/HANDOFF.md` — текущее незавершённое состояние.

Крупное решение отдельно фиксируется в `docs/decisions/`.

Изменение эпохи проекта отражается в `docs/PROJECT_EVOLUTION.md`.

## 6. AI audit trail

Каждый значимый запрос агенту сохраняется в:

`docs/ai_sessions/YYYY-MM-DD/NNN-<тема>-prompt.md`

Результат:

`docs/ai_sessions/YYYY-MM-DD/NNN-<тема>-response.md`

Response должен отражать не красивое резюме чата, а фактический результат:

- commit/branch/PR;
- изменённые сущности;
- проверки;
- ограничения;
- нерешённые вопросы.

## 7. Правило изменения документации

Документация не переписывает историю так, будто прежнего решения никогда не существовало.

Если стратегия изменилась:

- текущий канонический документ обновляется;
- в ADR фиксируется почему;
- в `PROJECT_EVOLUTION.md` остаётся след предыдущего этапа;
- старый release unit не редактируется так, чтобы потерять исторический смысл.

## 8. Правило миграции терминов

Если термин продукта меняется, например `Смыслы → Зачем`:

- сначала меняется канонический словарь и модель;
- затем schema/API;
- затем UI;
- legacy-поля удаляются только после доказанной миграции;
- в документации явно указано, что является legacy и что каноническим понятием.

Нельзя одновременно использовать два термина как равнозначные без пояснения.

## 9. Правило внешней инфраструктуры

Если агент меняет внешний сервис:

- состояние отражается в `docs/INFRASTRUCTURE_STATE.md`;
- секреты не записываются;
- указывается, какой commit/release соответствует изменению;
- для production-impacting действия фиксируется rollback.

Dashboard внешнего сервиса не заменяет git-документацию.

## 10. Правило исследования

Если новая статья, рекомендация или конкурентный паттерн меняют решение:

1. создаётся research note или обновляется Evidence Registry;
2. записывается оценка качества основания;
3. определяется влияние на ALIVE;
4. создаётся ADR, если меняется стратегия/архитектура;
5. обновляется hypothesis/roadmap при необходимости;
6. только после этого реализуется изменение.

## 11. Правило неполного знания

Если агент не может проверить важную вещь, он не должен:

- угадывать;
- объявлять gate закрытым;
- скрывать зависимость;
- заменять фактическую проверку уверенной формулировкой.

Нужно записать `НЕ ПРОВЕРЕНО`, причину и конкретный способ проверки.

## 12. Минимальный старт нового агента

Перед первым изменением новый агент должен уметь коротко сформулировать:

- что такое ALIVE;
- текущую продуктовую thesis;
- какой release принят в main;
- какой release сейчас строится;
- какой scope сейчас frozen;
- North Star;
- главные privacy/evidence ограничения;
- почему LLM пока не является core;
- что должно быть сделано следующим;
- когда должен состояться следующий backlog review.

Если это невозможно после чтения репозитория, сначала исправляется документация.

## 13. Конечный критерий continuity

> **Проект считается хорошо задокументированным, если смена AI-агента не требует от владельца заново объяснять продукт, историю решений, текущую архитектуру и незавершённую работу.**

# Протокол работы с product vision владельца

## 14. Владелец не обязан писать инженерное ТЗ

Владелец ALIVE работает как product owner/founder и может:

- формулировать идеи разговорно;
- добавлять новую мысль по ходу обсуждения;
- менять глубину product vision;
- исследовать несколько вариантов вслух;
- возвращаться к старой идее после нового понимания продукта.

Это **не считается ошибкой постановки задачи** и не должно искусственно ограничиваться ради удобства агента.

Агент обязан сам преобразовать product language в рабочий контракт.

Перед значимой реализацией агент должен извлечь и зафиксировать минимум:

- `GOAL` — какой пользовательский/продуктовый результат нужен;
- `SCOPE` — что именно входит сейчас;
- `INVARIANTS` — что нельзя сломать или переопределить;
- `ACCEPTANCE` — как объективно понять, что результат достигнут;
- `NON-GOALS` — что сознательно не делаем в этом release.

Если эти элементы уже выводятся из repo и сообщения владельца, **не задавать уточняющие вопросы ради формальности**.

## 15. Агент обязан классифицировать каждую новую существенную идею

Новая идея владельца во время разработки должна получить одну явную категорию:

### BLOCKER

Без неё текущий release нельзя корректно принять: нарушается безопасность, данные, основной пользовательский сценарий или acceptance criteria.

### SCOPE CORRECTION

Новая информация показывает, что текущий contract был сформулирован неверно или неполно.

### CURRENT SCOPE

Идея уже входит в зафиксированную цель и не расширяет release по смыслу.

### BACKLOG

Ценная идея, которую важно сохранить, но она не нужна для текущего gate.

### ROADMAP

Идея уже достаточно понятна и естественно относится к конкретному следующему этапу.

### RESEARCH

До product/technical commitment сначала нужны данные, исследование, user signal или spike.

По умолчанию, если идея **не нужна для acceptance текущего release**, она не должна расширять release и попадает в backlog/roadmap/research.

Агент коротко сообщает владельцу классификацию, но не превращает это в длинную бюрократию.

## 16. Freeze — ответственность агента, решение — владельца

Агент обязан сам предложить freeze, когда сформирован достаточно целостный проверяемый vertical slice.

Freeze означает:

- scope текущего release перестаёт автоматически расти;
- acceptance criteria становятся обязательным ориентиром;
- новые идеи продолжают свободно обсуждаться и сохраняться;
- реализация фокусируется на доведении frozen scope до Definition of Done.

Freeze **не означает запрет на product vision**.

Если новая вводная является `BLOCKER` или `SCOPE CORRECTION`, агент:

1. объясняет, какой контракт перестал быть корректным;
2. предлагает минимальное изменение scope;
3. обновляет implementation plan;
4. фиксирует, что именно было разморожено и почему;
5. после owner decision снова freeze-ит обновлённый scope.

Нельзя тихо расширять release под видом «небольшой доработки».

## 17. Backlog — живая очередь, а не архив

Канонический backlog: `docs/PRODUCT_BACKLOG.md`.

Агент обязан записывать туда релевантную идею **в момент появления**, а не просить владельца вспомнить её позже.

Каждый backlog item должен иметь хотя бы:

- смысл/ценность;
- почему не сейчас;
- статус;
- gate, на котором к нему нужно вернуться.

На каждом существенном release gate агент обязан открыть backlog и для релевантных пунктов предложить одно из:

- `PROMOTE` — включить в следующий release/roadmap;
- `KEEP` — оставить до более позднего gate;
- `RESEARCH` — сначала получить данные;
- `DROP` — отказаться с сохранённой причиной.

После promotion backlog должен ссылаться на новое каноническое место, а не содержать параллельную вторую спецификацию функции.

## 18. Последовательная реализация важнее количества одновременно начатых идей

По умолчанию агент должен доводить один основной user-facing delivery scope до одного из состояний:

- `DONE` — Definition of Done выполнен;
- `PARTIAL ACCEPTED` — owner явно принимает известные ограничения;
- `STOP/PIVOT` — evidence или новая информация делают продолжение нецелесообразным.

Только после этого агент предлагает следующий основной scope.

Запрещено без необходимости:

- начинать несколько конкурирующих UI shells;
- создавать параллельные реализации одной сущности;
- строить следующий крупный release, пока текущий завис на непроверенных gates;
- маскировать недоделанный текущий release большим объёмом новой функциональности.

## 19. Консервативное правило сохранения работающего продукта

Существующее подтверждённое поведение считается invariant, если изменение не требуется текущим contract.

Перед заменой, крупным refactor или redesign агент обязан:

1. определить существующий пользовательский и технический контракт;
2. перечислить затрагиваемые invariants;
3. определить regression checks;
4. предпочесть additive/минимальное изменение полной замене;
5. доказать необходимость замены, если она всё же нужна.

Нельзя создавать новый shell/экран/архитектурный обходной путь просто потому, что так быстрее реализовать новую функцию, если это теряет уже работающую функциональность или утверждённый UX.

## 20. Коммуникация с владельцем

Агент должен снижать, а не увеличивать управленческую нагрузку владельца.

Поэтому:

- не задавать вопрос, если ответ можно достоверно получить из repo, кода, документации или уже принятого решения;
- не просить владельца повторно пересказывать историю проекта;
- не требовать от владельца заранее перечислять все invariants — агент сначала восстанавливает их сам;
- не задавать серию мелких уточнений, если можно сделать безопасное разумное предположение и явно его записать;
- задавать вопрос прежде всего тогда, когда действительно нужен owner decision gate, существуют несколько существенно разных продуктовых вариантов либо цена ошибочного предположения высока;
- при появлении новой идеи коротко сообщать: `текущий release / backlog / roadmap / research` и почему;
- после завершения этапа самому возвращаться к backlog и предлагать следующий freeze candidate.

Правильная роль агента:

> **не заставлять владельца управлять памятью и микроскопическим scope вручную, а превращать непрерывный product vision в последовательную, проверяемую и обратимую разработку.**

## 21. Главный delivery loop

Рабочий цикл ALIVE:

> **Product vision → triage → release contract → owner freeze → implementation → verification → Definition of Done → backlog review → следующий proposed freeze.**

Владелец может продолжать генерировать vision на любом шаге. Агент обязан сохранять эти идеи, но не позволять им незаметно разрушать текущий delivery contract.
