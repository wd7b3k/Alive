# T-20260831-01 · [infra] Свести ветку бэкапов в main и снять противоречие в CURRENT_STATE

    Тип: задача
    Тема: infra
    Карточка доски: inf-backups
    Ветка: task/inf-backups
    Из разбора: нет
    Поставлено: 31.08.2026

## Почему задача существует

Бэкапы сделаны: `infra/backups/` — 14 файлов, коммит `2843802` («резервное копирование
с автоматической проверкой восстановления»), таймеры `habitoff-backup`, `habitoff-verify`,
`habitoff-report`, первый прогон сошёлся (3/3 пользователей, 45/45 таблиц, 51/51 миграций).

Не сделано другое: **эта работа живёт только на ветке `origin/docs/backups`** — 2 коммита
впереди `main` и 136 позади. В `origin/main` из всего слоя есть лишь
`infra/monitoring/checks/backups.sh`.

Отсюда противоречие внутри одного документа: `docs/CURRENT_STATE.md` строка 132 описывает
работающий `habitoff-backup`, а строки 556 и 587 утверждают «не настроены, восстановление
не проверялось». Пока это не сведено, каждая следующая сессия заново решает, закрыт ли
блокер пилота.

## Предпосылки — проверить первыми командами

- `git ls-tree -d origin/main infra/` — если `infra/backups` уже есть, остаётся только
  правка документов;
- `git rev-list --left-right --count origin/main...origin/docs/backups` — ожидается `136 2`;
- `ssh <VPS> 'systemctl list-timers habitoff-*'` — три таймера, следующий запуск в будущем;
- последний лог `habitoff-verify` — дата и результат последней проверки восстановления.

## Инварианты — нарушать нельзя

- восстановление проверяется на пустой базе, не на живой (`AGENTS.md`, дисциплина миграций);
- секреты и пароль шифрования в git не попадают (`AGENTS.md`, privacy-by-design);
- прод не правится руками: то, что работает на сервере, лежит в репозитории
  (`AGENTS.md`, REPO = единственный source of truth);
- статус карточки меняет коммит, а не рука (`docs/board/README.md`);
- 136 коммитов расхождения сводятся слиянием `main` в ветку, а не переписыванием истории
  (предложено — подтвердить).

## Что сделать

1. Влить `main` в `origin/docs/backups`, разрешить конфликты документации по правилу
   «факт инфраструктуры — из ветки бэкапов, факт продукта — из `main`».
2. Открыть PR ветки в `main` и влить.
3. Свести `docs/CURRENT_STATE.md`: строки 556 и 587 привести в соответствие с фактом,
   указать дату последней успешной проверки восстановления.
4. Обновить строку про бэкапы в `docs/NAVIGATOR.md`, раздел «Известные расхождения» —
   убрать закрытое.
5. Закрыть карточку трейлером `Board: done inf-backups` в том же коммите.

## Приёмка — команды и ожидаемый вывод

- `git ls-tree -d origin/main infra/` содержит `infra/backups`;
- `grep -n -i 'бэкап' docs/CURRENT_STATE.md` — ни одной строки, утверждающей «не настроены»;
- `systemctl list-timers habitoff-*` — три таймера, следующий запуск в будущем;
- вывод последнего `habitoff-verify`: пользователи N/N, таблицы N/N, миграции N/N;
- `node scripts/check-local-drift.mjs` — ноль неотправленного.

## Не делать

Не трогать перенос пользователей (`inf-users-migration`), мониторинг, юридический контур.
Найденное попутно — `Board: new` в том же коммите.

## Результат — заполняет исполнитель

**Ветка** `task/inf-backups` от `origin/docs/backups`.

**Коммиты**

- `a861a5e` — слияние `main` в ветку. Конфликт был один, `AGENTS.md`; разрешён в пользу
  `main`, из версии ветки сохранено правило «число, которое способна проверить машина,
  в документ не копируется» — перенесено в раздел «Evidence-first».
- `90e6270` — повторное слияние: пока шла работа, `origin/main` ушёл вперёд на четыре
  коммита (PR #69). Ровно тот случай, ради которого в `AGENTS.md` стоит правило про
  параллельные сессии.
- этот коммит — сведение документов и закрытие карточки.

**Расхождение предпосылок с фактом.** Постановка ожидала `136 2`; на момент работы было
`142 2`, к концу — `146 2`. Расхождение только в числе — `main` шёл вперёд, — поэтому
работа продолжена. Числа первого прогона из постановки (таблиц 45/45, миграций 51/51)
тоже устарели: на 30.08 сверка дала 46/46 и 54/54. Это и есть причина, по которой такие
числа больше не переносятся в документы.

**Приёмка**

- `infra/backups` в ветке есть, вне `docs/`, `infra/backups/` и `AGENTS.md` дерево
  совпадает с `origin/main` байт в байт — прикладной код слиянием не затронут;
- `grep -n -i 'бэкап' docs/CURRENT_STATE.md` — ни одной строки «не настроены»;
  противоречившие строки свелись слиянием в пользу ветки бэкапов;
- три таймера на сервере включены, следующий запуск у каждого в будущем:
  `habitoff-backup` 01.09 00:32 UTC, `habitoff-verify` 06.09 01:30 UTC,
  `habitoff-report` 07.09 06:00 UTC;
- `/var/lib/habitoff/last-verify` — `PASS`, копия `20260830-0034`, пользователи 3/3,
  таблицы 46/46, миграции 54/54, фактов 19; `Result=success`, 30.08.2026 01:38 UTC;
- `/srv/alive/backups/outbox` пуст — копии уезжают на Диск, очередь не копится;
- `node scripts/board.mjs check` — карточек 187, эпиков 13, ошибок нет;
- `node scripts/check-local-drift.mjs` — `task/inf-backups` числится локальной до пуша;
  остальные 74 места существовали до этой задачи.

**Найдено попутно, чинить отдельно.** `docs/CURRENT_STATE.md`, раздел «Что осталось до
полноценного прода», пункт 2 утверждает «наблюдаемости нет — первым мониторингом является
владелец с телефоном», хотя мониторинг работает с 28.08.2026 (ADR-0013) и виден из
админки с 30.08 (ADR-0016). Заведена карточка `current-state-otricaet-rabotayuschuyu`,
расхождение записано в `docs/NAVIGATOR.md`. В эту задачу не входит: постановка запрещает
трогать мониторинг.

**Незакрытое.** Установка на сервер не выполнялась и не требовалась: скрипты и юниты уже
стоят там с 27.08 — задача сводила репозиторий с фактом, а не наоборот. Раскатки
`main` на прод эта задача не делает.
