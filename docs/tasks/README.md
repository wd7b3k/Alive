# Постановки: разборы и задачи

Здесь живёт то, что раньше было промтом в чате. Промт как текст в чате нельзя проверить,
версионировать и связать с результатом; всё, что важно, теперь лежит в файле.

## Два типа

| Тип | Файл | Отвечает на вопрос | Чем заканчивается |
|---|---|---|---|
| Разбор | `R-ГГГГММДД-NN-<тема>-slug.md` | «что делать и надо ли» | решением, подвешиванием или отказом |
| Задача | `T-ГГГГММДД-NN-<тема>-slug.md` | «как это сделать и когда готово» | коммитом и `Board: done <id>` |

Разбор не порождает задачу автоматически. Задача заводится только после строки «Решение».
Это и есть место для привычного цикла: спросил → почитал → подвесил → вернулся.

## Тема

Тема — тот же список, что `epic` на доске. Она стоит и в имени файла, и в шапке, поэтому
эволюция направления читается одной командой:

```bash
ls docs/tasks | grep -- -money-        # всё по монетизации в хронологии
node scripts/tasks.mjs                 # всё по темам, со статусами
```

Действующие темы: `infra` `process` `design` `content` `pilot` `seo` `brand` `perf`
`release` `auth` `flow` `privacy` `money` `legal` `knowledge` `social`.

Новая тема заводится решением владельца и добавляется в этот список — не по ходу работы.
Тема не меняется у уже заведённого файла: иначе история направления рвётся.

## Статусы разбора

- **открыт** — вопрос задан, решения нет;
- **решение принято** — есть строка «Решение», ADR и правки документов; дальше живут задачи;
- **подвешено** — сознательная пауза. Обязательны два поля: что нельзя делать, пока
  подвешено, и какой факт снимает паузу;
- **отклонено** — с причиной, чтобы не возвращаться к тому же кругу через месяц.

Подвешенное решение — нормальная позиция, но у неё есть цена: работы, опирающиеся на него,
становятся мусором, если решение будет другим. Поэтому раздел «что нельзя делать» —
не формальность.

## Правила

- одна задача — один файл, одна ветка `task/<id карточки>`, одна карточка доски;
- Коду задача передаётся одной строкой: «работай по `docs/tasks/T-…md` в ветке `task/<id>`»;
- предпосылки проверяются первыми командами сессии;
- нет доступа, которым результат доставляется, — задача не берётся;
- файл заводится до работы и коммитится; после закрытия не удаляется — он и есть история.

## Как рождается постановка

Владелец пишет коротко — одной-двумя фразами. Постановку по шаблону собирает Claude, а не
владелец:

- **инварианты предлагаются, а не запрашиваются.** Источник — `AGENTS.md`,
  `docs/PRODUCT_PRINCIPLES.md` (P1–P20), действующие ADR, документы направления. Каждая
  строка со ссылкой на источник; строка без источника помечается «предложено — подтвердить»;
- **вопросов не больше трёх**, и только те, ответ на которые меняет работу. Всё остальное —
  явное допущение в тексте постановки, а не вопрос;
- **предпосылки проверяются, а не предполагаются**: если факт можно взять командой в
  репозитории, он берётся командой до того, как попадёт в постановку;
- владельцу остаётся вычеркнуть лишнее и сказать «делаем».

## Доступы контура

Про доступы владельца не спрашивают: они постоянные. Разные у постановщика и исполнителя —
это и есть причина, по которой раздел в карточке остаётся.

| | Постановщик (сессия в облаке, shell на машине владельца) | Исполнитель (Claude Code на машине владельца) |
|---|---|---|
| Файлы репозитория | чтение и запись | чтение и запись |
| Удаление файлов | **нет** (`rm` запрещён) | есть |
| `git` чтение, `fetch`, ветки, worktree | есть | есть |
| `git push` | **нет** (учётных данных в этом shell нет) | есть |
| `gh` | нет | есть |
| Прод `habitoff.ru` | **нет**, 403 | есть |
| `ssh` на VPS | **нет**, сеть недоступна | есть |

Проверено 31.08.2026 командами; `scripts/state.sh` показывает актуальное состояние.

Следствия: постановщик не делает выводов о состоянии прода и сервера — только о репозитории;
доведение до `origin` и всё, что касается сервера, выполняет исполнитель.
