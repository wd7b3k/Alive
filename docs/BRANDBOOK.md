# ALIVE — брендбук и визуальный контракт

Статус: **канонический документ для всех пользовательских интерфейсов ALIVE**

Основание: утверждённый визуальный язык ALIVE v3.0, существующий `RedesignApp.tsx`, `redesign.css`, утверждённый logo asset и продуктовые принципы проекта

Этот документ обязателен для Web, Telegram, мобильных приложений и любых будущих клиентских интерфейсов. Он определяет не только внешний вид, но и характер продукта: ALIVE должен ощущаться как спокойная, зрелая, точная система возвращения выбора, а не как quit-tracker, wellness-приложение, медицинская панель или игровая мотивационная механика

---

# 1. Суть бренда

ALIVE — не приложение про запреты и не приложение про «силу воли»

ALIVE помогает человеку заметить автоматизм немного раньше, понять функцию привычки и вернуть пространство для другого решения

Ключевой образ бренда:

> **Тёмное спокойное пространство, в котором один следующий выбор становится заметнее**

Бренд должен создавать четыре ощущения:

- спокойствие без сонливости
- ясность без холодной клиничности
- сила без агрессии
- технологичность без ощущения лабораторного интерфейса

ALIVE не должен создавать ощущения:

- фитнес-трекера
- казино или streak-game
- медицинской CRM
- дешёвого wellness
- инфопродукта
- приложения для наказания себя
- социальной сети
- корпоративной BI-панели

---

# 2. Основной визуальный принцип

Визуальная система v3.0 является **базовой и замороженной**

Новые функции должны входить в неё как новые карточки, маршруты, состояния и данные, а не создавать новую оболочку

Главное правило:

> **Новая функция не является поводом менять визуальный язык существующего экрана**

Если задача может быть решена через существующие паттерны `r-header`, `r-page`, `r-section`, `r-now`, `r-button`, `r-modal`, `r-choice-grid`, `r-episode-card` и другие утверждённые компоненты — используются они

Создание нового root shell, новой дизайн-системы или параллельного набора базовых компонентов требует отдельного согласования владельца

# 3. Каноническая палитра

Источник истины — tokens из `app/src/redesign.css`

## Фон

- `--r-bg: #061013` — основной фон
- `--r-bg2: #09171b` — дополнительный фон

Фон почти чёрный, но не абсолютный `#000`

Он должен сохранять лёгкий зелёно-сине-графитовый оттенок

Используется мягкий радиальный gradient, а не плоская чёрная заливка

## Поверхности

- `--r-surface: #0d1b1f`
- `--r-surface2: #112329`
- `--r-soft: #152a2f`

Карточки должны быть тёмными

**Запрещено без отдельного согласования:**

- белые карточки
- светло-серые крупные панели
- cream/beige knowledge cards
- светлые modal surfaces
- превращение Facts/Myths в отдельную светлую дизайн-систему

## Текст

- `--r-text: #f4f7f5` — основной
- `--r-muted: #a4b6b5` — вторичный
- `--r-dim: #718584` — tertiary / подписи / metadata

Нельзя делать основной текст чисто белым повсеместно

Контраст строится через иерархию, а не через максимальную яркость каждого элемента

## Акцентные цвета

- `--r-lime: #c9ff5b`
- `--r-lime2: #9eea47`
- `--r-teal: #51ddd0`
- `--r-amber: #f2ca69`
- `--r-red: #f09a9a`

### Lime

Главный action color

Используется для:

- основного CTA
- позитивного выбора
- active/progress emphasis
- действительно важного action state

Не используется как декоративная заливка большого количества карточек

На одном экране желательно иметь **один главный lime-акцент**

### Teal

Вторичный интеллектуальный акцент

Используется для:

- ссылок
- kicker
- attention/insight элементов
- вторичных активных состояний
- icon surfaces

### Amber

Используется для:

- факта употребления никотина
- осторожных предупреждений
- контекстных состояний, требующих внимания

Amber не означает «провал»

### Red

Используется крайне редко

Только для:

- destructive action
- удаления
- реальной ошибки

Нельзя использовать red для lapse, плохой недели, высокого baseline или отсутствия прогресса

# 4. Типографика

Основная гарнитура:

`Inter, ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, Segoe UI, sans-serif`

Если Inter недоступен, используется системный sans-serif без визуального скачка

## Заголовки

Характер:

- крупные
- плотные
- короткие
- низкий line-height
- отрицательный tracking
- без декоративности

Канонический крупный диапазон:

`clamp(38px, 5vw, 64px)`

Для hero Today:

`clamp(38px, 4.6vw, 59px)`

Главный экран не должен превращаться в рекламный лендинг с огромной типографикой больше существующего v3.0 масштаба

## Section headings

Ориентир:

`23–31px`

## Body

Обычно:

`13–16px`

Главный explanatory body:

`16px`, line-height около `1.6`

## Kicker

Канонический стиль:

- 10–11px
- uppercase
- высокий weight
- tracking около `.14em`
- мягкий teal

Kicker — редкий структурный сигнал, а не декоративный шум

---

# 5. Язык и копирайтинг

Весь пользовательский интерфейс ALIVE — **на русском языке**

Исключения возможны только для:

- названий препаратов, если русский вариант некорректен
- технических обозначений в методологии
- DOI / названий исследований

В основных UI-текстах нельзя использовать внутреннюю разработческую лексику без объяснения

## Характер речи

ALIVE говорит:

- коротко
- спокойно
- конкретно
- без сюсюканья
- без психотерапевтического канцелярита
- без мотивационного пафоса
- без обвинения
- без псевдомедицинской категоричности

Примеры хорошего языка:

- `Хочу закурить`
- `Никотин уже был`
- `Что сейчас нужно`
- `Что получилось`
- `В похожих ситуациях это уже помогало`
- `Это данные, не обнуление`

Примеры плохого языка:

- `Меня тянет`
- `У меня возник импульс`
- `Начать интервенцию`
- `Проработать craving`
- `Ты сорвался`
- `Ты снова проиграл`
- `Начни с нуля`

## Заголовки без точек

Завершающие точки в UI-заголовках запрещены

Не:

`Что происходит сейчас.`

А:

`Что происходит сейчас`

## Длина

В момент тяги:

- один вопрос
- один смысл
- одно короткое объяснение

Длинная методология открывается через progressive disclosure

---

# 6. Пространство и сетка

Каноническая desktop ширина:

`1160px`

Основной контейнер:

`width: min(1160px, calc(100% - 40px))`

Страница не должна растягиваться на всю ширину большого монитора

Основной вертикальный rhythm строится через:

- 18px между крупными блоками
- 10–14px внутри компактных grids
- 19–25px padding обычных cards
- около 42px padding главного Today hero

Нельзя без причины делать экран более плотным, чем v3.0

ALIVE должен сохранять визуальный воздух

---

# 7. Радиусы

Визуальный язык ALIVE мягкий, но не «пузырчатый»

Канонические диапазоны:

- hero: около `30px`
- крупная section: `24px`
- action card: `18–22px`
- small controls: `11–15px`
- pills: `999px` только там, где pill действительно оправдан

Нельзя делать все элементы одинаково круглыми

---

# 8. Границы и глубина

Карточки отделяются не яркими рамками, а сочетанием:

- очень мягкой полупрозрачной линии
- тёмной поверхности
- слабого gradient
- умеренной тени

Канонический border family:

`rgba(145,211,203,.14)`

Hero может иметь более выраженную teal-border

Тени глубокие и очень мягкие

Нельзя использовать:

- жёсткие серые borders
- Material-style elevation
- белые drop shadows
- кислотные glow вокруг большинства элементов

---

# 9. Главный экран Сегодня

`Сегодня` — главное рабочее пространство продукта

Его структура v3.0 является утверждённой

Ключевые элементы:

- крупный hero
- спокойный текст слева
- основной lime CTA справа
- два secondary actions
- pulse/summary cards ниже
- карта внимания / сценариев ниже
- реальные эпизоды и аналитика после first-action layer

Новые данные не должны разрушать эту композицию

## Hero

Hero — тёмный

Запрещено делать его светлым

Он не является promo banner

## Главный CTA

Главный CTA — самый заметный элемент экрана

Для сигарет:

`Хочу закурить`

Для vape:

`Хочу затянуться`

Для кальяна:

`Хочу покурить кальян`

Если у пользователя несколько target products, выбор product разрешается внутри flow, но CTA должен оставаться человеческим и конкретным

## Secondary actions

`Никотин уже был` и `Итоги дня` остаются визуально вторичными

Их нельзя делать равными по силе основному craving CTA

---

# 10. Карточки и секции

Каждая карточка должна отвечать на один вопрос

Не создавать card salad

Карта состоит из:

- ясного label
- главного значения или действия
- короткого explanatory text

Если карточка содержит больше 2–3 смысловых уровней, вероятно нужен details/secondary screen

## Facts

Facts должны выглядеть как часть ALIVE, а не как внешний медицинский справочник

Использовать тёмные `r-section` / `r-episode-card`-подобные surfaces

Типы фактов можно различать тонким акцентом:

- benefit → lime/teal
- risk → amber/neutral
- mechanism → teal

Никаких белых карточек

## Myths

Миф — не warning alert

Его визуальная модель:

- тёмная карточка
- небольшая amber/teal отметка
- тезис
- короткий reframe
- `Почему так` / `Источник`

Мифы не должны визуально стыдить пользователя

## Вместе

`Вместе` не выглядит как leaderboard или social feed

Использовать:

- спокойные aggregate cards
- те же тёмные поверхности
- небольшие group metrics
- один личный comparison block

Не использовать яркие podium/rank colors

---

# 11. Модальные сценарии и craving flow

Craving flow — рабочий инструмент, а не wizard из enterprise software

Модалка должна сохранять существующую темную surface и визуальный язык `r-modal`

## Progress

Progress должен быть заметен, но встроен в интерфейс

Предпочтительная форма:

- `Шаг 3 из 6`
- короткий lime/teal progress line
- кликабельные уже пройденные этапы

Не создавать отдельную большую светлую панель progress поверх модалки

Stepper должен выглядеть частью модального интерфейса

## Back navigation

Все пройденные этапы доступны для возврата

При изменении upstream answer зависимые ответы invalidated автоматически

UX не должен заставлять пользователя закрывать flow и начинать заново

---

# 12. Иконки

Используется единый текущий icon vocabulary из `ui-icons`

Иконки:

- line/simple
- без цветных иллюстраций
- без emoji в основных control surfaces
- обычно 18–25px

Нельзя в одном интерфейсе смешивать несколько icon packs без отдельной причины

---

# 13. Логотип

Утверждённый ALIVE logo asset не перерисовывается и не генерируется заново

Канонический source asset находится в repo

Logo должен:

- быть видимым на login
- быть видимым в authenticated header
- сохранять aspect ratio
- не обрезаться
- не заменяться текстовым wordmark

Любая проблема логотипа сначала диагностируется как asset/build/layout/runtime issue

Не «чинить» логотип новым изображением

---

# 14. Навигация

Desktop navigation остаётся компактной и центрированной

При росте количества разделов сначала проверяется information architecture, а не просто добавляется всё в одну длинную строку

Для верхнего уровня допустимы только действительно ключевые рабочие пространства

Если навигация перестаёт помещаться спокойно, secondary knowledge/settings разделы переносятся в appropriate secondary navigation

Mobile — отдельный сценарий

Нельзя переносить desktop navbar на mobile один к одному

---

# 15. Mobile first для момента тяги

Mobile — главный realtime surface для craving flow

Требования:

- CTA виден без поиска
- tap targets не меньше примерно 44px
- modal не выходит за safe area
- progress читается
- stepper не превращается в шесть микроскопических подписей
- 6 пунктов нижней навигации не должны быть механически ужаты до нечитаемого состояния

Если навигационных разделов становится много, использовать другой IA pattern вместо уменьшения текста

---

# 16. Motion

Анимация функциональная и короткая

Допустимо:

- 150–250ms
- небольшое смещение hover
- мягкое изменение progress
- fade/scale modal

Запрещено:

- bounce
- confetti
- celebratory fireworks
- spinning counters
- streak flames
- attention-grabbing endless animation

ALIVE не должен формировать дополнительную зависимость от интерфейса

---

# 17. Состояния и семантика цвета

## Success

Lime

Означает:

- выбор остался у пользователя
- action completed
- positive signal

Не означает моральную «правильность» человека

## Nicotine used

Amber

Означает факт употребления

Не означает failure

## Destructive

Red

Только удаление/ошибка

## Empty

Neutral dark

Empty state всегда объясняет, что нужно сделать дальше

---

# 18. Medical and evidence UI

Evidence не должен визуально превращать ALIVE в клинический кабинет

Исследования и источники показываются через progressive disclosure

На карточке:

- человеческий тезис
- короткое объяснение
- источник по запросу

Не выводить DOI крупным текстом на основном экране

Evidence labels должны быть русскими и понятными

Пример:

- `Хорошо изучено`
- `Есть данные для этого состояния`
- `Экспериментальная Замена ALIVE`

---

# 19. Anti-patterns

Без прямого согласования владельца запрещено:

- создавать новый root app/shell вместо существующего
- переписывать `Сегодня` ради добавления одной функции
- создавать параллельную палитру
- использовать светлые карточки на тёмном фоне как новый основной паттерн
- менять scale заголовков
- перестраивать header
- заменять утверждённый logo
- смешивать три разных визуальных языка на одной странице
- увеличивать количество primary CTA
- превращать `Вместе` в leaderboard
- превращать Facts в scareware
- превращать Myths в агрессивное опровержение пользователя
- внедрять новый UI framework только ради одной функции
- добавлять новую дизайн-систему поверх `redesign.css`

---

# 20. Правило additive releases

Начиная с v3.0, любой frontend release считается **additive by default**

Перед изменением существующего экрана разработчик обязан определить:

1. какой конкретный существующий компонент изменяется
2. почему нельзя использовать его без structural rewrite
3. какие утверждённые функции он уже содержит
4. какие regression tests защищают эти функции
5. какой screenshot/visual reference является baseline

Если ответ на эти вопросы не записан, structural rewrite запрещён

---

# 21. UI regression gate

До каждого frontend PR обязательны:

## Функциональный diff

Список функций существующего экрана до изменения

Для `Сегодня` минимум:

- основной craving entry
- quick nicotine entry
- evening check-in
- pulse metrics
- baseline comparison
- Freedom Fund / экономия где предусмотрено текущей версией
- карта внимания / trigger entry
- episode history
- delete/correction semantics
- navigation to Links / Path / Meanings / Method / Profile

Новый release не может молча удалить любой из этих элементов

## Visual diff

Сравнить минимум:

- desktop Today
- mobile Today
- craving modal
- profile
- login

Критерий:

> новые функции выглядят как естественная часть того же продукта

## Owner gate

Если новый экран визуально воспринимается как другая версия продукта, требуется согласование до merge

---

# 22. Source of truth для дизайна

При расхождении источников приоритет:

1. прямое последнее решение владельца
2. этот `BRANDBOOK.md`
3. production-approved `RedesignApp.tsx` и `redesign.css` v3.0
4. `PRODUCT_PRINCIPLES.md`
5. release-specific UI notes
6. любые новые предложения AI

AI не имеет права считать собственную новую композицию более актуальной только потому, что она создана позже

---

# 23. Применение к будущим клиентам

Web, Telegram и mobile не обязаны пиксельно повторять друг друга

Они обязаны сохранять одинаковую идентичность:

- тёмный спокойный visual tone
- lime как главный action
- teal как secondary insight color
- отсутствие shame
- короткий русский язык
- одинаковая семантика сущностей
- одинаковая продуктовая логика

Telegram может использовать более простую композицию

Native mobile может использовать platform-native navigation

Но они не должны становиться отдельными брендами

---

# 24. Короткая проверка перед любой UI-правкой

Перед commit ответить:

- Я расширяю существующий интерфейс или заменяю его
- Сохранились ли все функции предыдущего релиза
- Использую ли я каноническую палитру
- Остались ли поверхности тёмными
- Есть ли только один главный lime CTA
- Сохранилась ли типографическая иерархия
- Все ли тексты естественно написаны по-русски
- Нет ли точек в заголовках
- Не создал ли я новый shell без необходимости
- Проверил ли я desktop и mobile
- Могу ли я визуально поставить новый экран рядом с v3.0 и сказать, что это один продукт

Если последний ответ неочевиден — изменение не готово
