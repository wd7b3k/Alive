# Сеть агентов Habitoff

Роли лежат рядом файлами `<имя>.md`. Общие правила — `AGENTS.md`, раздел «Сеть агентов»;
здесь карта: кто за что отвечает, кому какой файл принадлежит, какая модель и как роль
подключается сама.

Роль не пересказывает `AGENTS.md`. Инварианты, таблица «правило → проверка», git и гейты
владельца действуют для всех и живут в одном месте.

## Как роль подключается сама

Роль вызывается не руками, а по описанию: главный агент читает поле `description` каждой
роли и сам решает, кому отдать работу. Поэтому описание — не подпись к роли, а условие
её включения: в нём перечислены слова и события, при которых роль обязана вступить, и
стоит документированная формулировка автоделегирования `Use proactively`.

Следствия, о которых нужно знать:

- **описание — единственный рычаг автозапуска.** Хуков и настроек, которые включали бы
  роль принудительно, для этого нет; есть только обратное — запрет роли в `settings.json`;
- **роль не видит истории разговора.** В её контекст попадают: собственный файл, задание,
  которое ей передали, `CLAUDE.md` и предзагруженный скилл `habitoff-vhod`. Всё
  остальное — состояние, постановка, документы по теме — она берёт сама командами и
  чтением. Поэтому первый шаг любой роли одинаков: вход по `habitoff-vhod`;
- **роль не выбирает себе модель на ходу.** Модель записана в файле. Задача выше уровня —
  роль останавливается и возвращает её с пометкой «нужна модель выше».

## Порядок в сессии

```
sostoyanie  →  postanovka  →  роль направления  →  priyomka
   снимок        R- / T-           работа          проверка и прод
```

`sostoyanie` включается первой всегда. `priyomka` — последней всегда, и она же доводит
работу до прода: без неё задача остаётся написанной, а не сделанной. Между ними работает
одна роль направления; задача, задевающая два направления, делится на две задачи, а не
отдаётся двум ролям сразу.

## Кто чем владеет

Файл правит только его владелец. Другая роль, которой нужна правка, просит её у владельца
или переоформляет задачу. Это правило существует потому, что двойное владение уже дважды
приводило к затиранию работы (`docs/INCIDENTS.md`, класс 7).

## Скиллы

Каждой роли предзагружен `habitoff-vhod` (`.claude/skills/habitoff-vhod/`) — порядок входа
в контекст и команды, которыми берётся факт. Он не дублирует правила, а говорит, где они
лежат: роль не видит разговора и обязана собрать состояние сама.

Предметные скиллы (работа с документами, диаграммами, браузером) подключаются той же
строкой `skills:`, когда они установлены в контуре владельца. Список установленного
проверяется командой `/agents` и меню скиллов в Claude Code — из облачной сессии он не
виден, поэтому в ролях сейчас стоит только тот скилл, который лежит в этом репозитории.

## Почему модель такая

Модель выбрана по цене ошибки, а не по объёму текста. `opus` там, где ошибка необратима
или дорого стоит: миграции и прод, юридический текст, медицинские утверждения, постановка
(три из трёх случаев «построили вторую сущность» родились в ней), стратегия и язык
продукта. `sonnet` там, где ошибка ловится проверкой в том же заходе: код с зелёными
тестами, вёрстка, разметка, сводка состояния, приёмка по регламенту.

## Чего в сети нет и почему

- **ASO.** Продукт не идёт в магазины приложений: видимость PWA его заменяет. Вместо
  ASO у роли `vidimost` есть AISO — цитируемость страниц языковыми моделями.
- **Отдельного «тестировщика» и отдельного «релиз-инженера».** Это одна роль `priyomka`:
  разделение проверки и доставки — ровно тот шов, на котором работа застревала в ветках.
- **Отдельного «администратора процессов».** Это `sostoyanie` плюс проверки в CI:
  администрирование, которое держится на роли, а не на команде, уже не удержалось.
