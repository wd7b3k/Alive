# Выкладка

`deploy.sh` здесь — канонический. `/srv/alive/deploy.sh` является его копией и
обновляется установкой из репозитория, а не правкой на сервере: до 30.08.2026 скрипт в
git не отражался вовсе, и разобрать оборванную выкладку можно было только чтением файла
по ssh.

## От кого запускается

**От владельца `/srv/alive/repo`, то есть от `alive`. Не от root.** Скрипт проверяет это
первым делом и отказывается работать иначе.

Причина не в аккуратности. `git` отказывается читать репозиторий, принадлежащий другому
пользователю, — `detected dubious ownership`. `sudo deploy.sh` сохраняет `SUDO_UID`, по
нему git признаёт каталог своим и всё работает; запуск из root-сессии, где `SUDO_UID`
нет, ломает каждую git-команду. Разбирать эти случаи по отдельности незачем: прав root
выкладке не нужно ни для чего.

Вторая половина той же беды тише и живёт дольше: `npm ci` и сборка от root оставляют в
репозитории тысячи файлов чужого владельца, и следующая выкладка от `alive` падает уже
на них. 30.08 таких файлов осталось 9525.

```bash
ssh alive@habitoff.ru
cd /srv/alive/repo && git checkout main && git fetch origin && git merge --ff-only origin/main && /srv/alive/deploy.sh
```

## Что скрипт проверяет и в каком порядке

| Шаг | Отказ означает |
|---|---|
| запуск не от root, владелец каталога == текущий пользователь | иначе git не прочитает репозиторий, а сборка испортит владельца |
| установленный `/srv/alive/deploy.sh` совпадает с репозиторным | копия молча устарела и делает не то, что описано |
| `git rev-parse HEAD` отвечает | пока это неизвестно, ни одному ответу про дерево верить нельзя |
| ветка — `main` | прод собирается только с main (`RELEASE_POLICY` §5) |
| `git status --porcelain` **по коду возврата** | нельзя выложить то, чего нет в коммите |
| `git fetch origin main` прошёл **и** `HEAD` == `origin/main` | собрался бы не тот коммит: клон отстал, ушёл вперёд или свежесть ссылки неизвестна |
| число файлов миграций == число записей в базе | репозиторий и база разъехались |
| сборка прошла | |
| `dist/version.json` содержит непустой commit, равный HEAD | сборка без отпечатка на прод не идёт |
| entry-чанк из `index.html` лежит в `dist/assets` | половина сборки выглядит как целая до первого запроса |
| разложенный каталог полон | |
| **только теперь** переключается симлинк | до этого момента любой отказ оставляет прод нетронутым |

## Почему `fetch` скрипт делает сам, а `pull` — не делает

Гейты про ветку и грязное дерево отвечают на вопрос «соответствует ли дерево своему
коммиту». Ни один не отвечает на вопрос «тот ли это коммит». 06.09.2026 выкладка собрала
`f76f8b7`, когда в `origin/main` лежал `d5aeed7`: дерево было чистым, ветка — `main`, клон
отставал на 22 коммита, скрипт напечатал «выложено», прод не сдвинулся. Тот же дефект с
другой стороны — упавший `git pull` в однострочнике выше: команда отказала, человек не
заметил, скрипт пересобрал прежний коммит и снова отчитался успехом.

**`fetch` делает сам скрипт**, иначе гейт сверяется со ссылкой неизвестной свежести и
молча пропускает ровно тот случай, ради которого написан. Ссылку обновляет ещё и
мониторинг (`infra/monitoring/lib/fingerprint.sh`), но выкладка не имеет права зависеть от
того, успел ли пройти чужой таймер. Сверка идёт с `FETCH_HEAD` — его пишет этот самый
`fetch` и всегда, тогда как `refs/remotes/origin/main` обновляется попутно и зависит от
refspec клона.

**`pull` скрипт не делает.** Рубеж, который сам чинит то, на что жалуется, перестаёт быть
рубежом: выкладка молча увозила бы на прод всё, что оказалось в `origin/main`, включая то,
чего человек выкладывать не собирался. Скрипт отказывает и печатает готовую команду — тот
же приём, что в гейте устаревшей копии самого себя.

**Отказ `fetch` — это отказ выкладки**, а не «сверюсь с тем, что есть»: свежесть ссылки
неизвестна, значит результат сверки ничего не значит. Ожидание ограничено
`HABITOFF_FETCH_TIMEOUT` (по умолчанию 60 с), чтобы недоступный GitHub давал отказ, а не
висящую выкладку. Аварийного обхода нет намеренно.

## Чем это отличается от версии, работавшей до 30.08.2026

Гейт грязного дерева был написан так:

```bash
[[ -z "$(git status --porcelain)" ]] || { echo "ОТКАЗ: рабочее дерево грязное"; exit 1; }
```

Упавший `git` пишет в stderr и в stdout не печатает ничего. Подстановка пуста, условие
истинно, гейт доволен. Проверка пропускала ровно тот случай, ради которого написана: когда
о состоянии дерева не известно ничего. 30.08 в 18:02 так и вышло — сборка собралась из
того, что лежало в каталоге, `version.json` получил пустой `commit`, симлинк переключился,
и прод отдавал сборку без имени.

Отсюда правило, которому подчинён весь файл: **ни одна команда не проверяется по своему
выводу, только по коду возврата.**

## Установка

```bash
sudo install -m 755 -o alive -g alive /srv/alive/repo/infra/deploy/deploy.sh /srv/alive/deploy.sh
```

**Повторять при каждом изменении этого файла.** `/srv/alive/deploy.sh` — копия, и копия
молча устаревает: 31.08.2026 в репозиторий добавился шаг выгрузки каталога, `main` уехал
на прод, а выкладку делала копия без этого шага — разметка собралась без источников, и по
логу выкладки этого было не видно, потому что шага там просто не было.

Теперь скрипт сверяет себя с репозиторием и отказывается работать, если копия разошлась.
Сам себя он не переустанавливает: переустанавливать себя на ходу — это менять файл, из
которого читается текущая команда.

## Как убедиться, что гейт работает

Проверка проверки — не формальность: предыдущий гейт выглядел рабочим три месяца.

```bash
# 1. грязное дерево
touch /srv/alive/repo/.deploy-gate-test
/srv/alive/deploy.sh; echo "код $?"          # ненулевой, current не тронут
rm /srv/alive/repo/.deploy-gate-test

# 2. git недоступен
GIT_DIR=/nonexistent /srv/alive/deploy.sh; echo "код $?"

# 3. запуск от root — тот самый случай 30.08
sudo -n env -u SUDO_UID -u SUDO_USER /srv/alive/deploy.sh; echo "код $?"

# 4. клон отстал от origin/main — случай 06.09
cd /srv/alive/repo && git reset --hard HEAD~1
/srv/alive/deploy.sh; echo "код $?"          # ОТКАЗ с двумя SHA, до npm ci не дошло
git pull --ff-only origin main

# 5. origin недостижим — гейт обязан отказать, а не сверяться с протухшей ссылкой
GIT_SSH_COMMAND=/bin/false /srv/alive/deploy.sh; echo "код $?"   # ОТКАЗ «fetch не прошёл»
```

После каждой — `readlink -f /srv/alive/current` обязан показывать тот же релиз, что и до,
а `builtAt` на `https://habitoff.ru/version.json` — остаться прежним.

## Откат

```bash
ln -sfn /srv/alive/releases/<предыдущая> /srv/alive/current.new
mv -Tf /srv/alive/current.new /srv/alive/current
```

Миграции откату не подлежат — `docs/RELEASE_POLICY.md` §6.
