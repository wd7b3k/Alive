# Rollback

Выпуск содержит migrations и изменения данных, поэтому откат фронтенда и откат базы —
разные операции, и второй нужен далеко не всегда.

## Точки возврата

- production commit до выпуска: `f267214` (мерж PR #17);
- production commit выпуска: `428af9e` (мерж PR #20);
- Cloudflare Pages хранит предыдущие deployment'ы проекта `alive-aw2` — откат делается
  выбором последнего успешного deployment на `f267214`.

## Откат интерфейса

1. В Cloudflare Pages выбрать deployment коммита `f267214` и выполнить rollback.
2. Создать revert-PR на `main`; историю `main` не переписывать.
3. Базу при этом не трогать: интерфейс `f267214` не знает о `goals_catalog`, но всё,
   что он читает, на месте.

## Откат базы

Полный откат схемы не предусмотрен и не нужен: все миграции выпуска аддитивны, кроме
`20260825140000` (нормализация библиографии), которая удаляет три колонки. Перед
удалением она делает резервные таблицы `*_backup_20260825` — они лежат в базе и на
момент выпуска не удалены именно поэтому.

Восстановление колонок:

1. `alter table public.facts_catalog add column source_title text, add column source_url text, add column doi text;`
   и то же для `myths_catalog`; для `replacements_catalog` — только `source_title` и
   `source_url`.
2. Заполнить из `public.facts_catalog_backup_20260825` и соседних по `code`.
3. Удалить внешние ключи `source_id` только после того, как значения восстановлены.

Резервные таблицы удаляются лишь после того, как владелец принял новые тексты. Пока они
есть, откат содержательной части — операция на минуты.

## Что откатить нельзя

Записи в `supabase_migrations.schema_migrations` — бухгалтерия, а не данные. Если
откатывается схема, соответствующие версии удаляются оттуда вручную, иначе следующий
`db push` пропустит их.
